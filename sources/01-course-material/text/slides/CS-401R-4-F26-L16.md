## Slide 5
- Hosting, Deployment, Serving Across AI Systems
> Notes: QUESTION: What does serving mean for a churn model, an LLM application, and an agent, and how does it differ from deployment and hosting?  One minute here. Deployment was covered earlier in the course; today is the serving row. Use the three columns as the road map for the session: classical ML first, then LLMs, then agents. The definitions remain consistent across all three columns: deployment releases a system version, hosting provides its execution environment, and serving runs it for requests or tasks. What changes is the scope of the system.  Start with traditional ML.For NorthStar’s churn model, we deploy the approved model artifact, dependencies, and inference code. Hosting provides the compute and runtime. Serving processes customer features and produces churn probabilities.  Move to LLM and RAG systems.Here, a release can change application behavior without changing model weights. Updating a prompt, selecting a different model, or changing retrieval settings can all affect production results. When we use a hosted model API, the provider hosts and serves the underlying model. Our team still deploys and operates the application that calls it. With RAG, we also operate—or use managed services for—the retrieval infrastructure. Serving now includes assembling context, constructing the prompt, generating the response, and checking the output. Retrieval applies specifically to RAG; a plain LLM application may omit that step. For NorthStar’s offer generator, a release might introduce a new prompt and retrieval configuration. Those components must work with the selected model and knowledge index. Serving then means retrieving context, building the prompt, generating, and validating the result.  Move to agents.An agent release includes orchestration, instructions, tool definitions, permissions, and policies. Memory configuration is part of the system design; accumulated user or session data is runtime state and needs separate management. Hosting supports the agent runtime, session state, and access to tools and models. Serving becomes a potentially multistep task: choose an action, call a tool, observe the result, and continue, finish, or escalate. The loop shown is a common pattern; not every agent uses an explicit planning step. For NorthStar’s customer-service agent, one request might involve looking up an order, checking refund eligibility, and requesting approval before taking action. We therefore monitor task completion, tool failures, execution limits, and cost per task alongside latency.   A few points tend to blur the lines: Managed platforms collapse the layers. With SageMaker or Vertex AI, one API call provisions hosting, deploys the model, and starts serving. Students often think it’s one thing because the tooling hides the seams. Hosting constrains the other two. Your GPU type limits which serving optimizations are possible (quantization, tensor parallelism), and your environment determines which rollout strategies are practical. With API-hosted foundation models, you only own a slice. Using Bedrock or the Claude API, the provider handles hosting and serving. Your “deployment” shrinks to versioning prompts, configs, and model IDs, which is a useful contrast with traditional MLOps.  Shorthand: hosting is the place, deployment is the move, serving is the work.   Ask the class:“If we change an agent’s refund permissions without changing its model, is that a deployment?” Yes. We have changed the production system’s configuration and authority, even though the model is the same. TRANSITION: Start with the serving row for classical ML. ## Slide 8
- Serverless Inference: The Low-Traffic Option
- No traffic, no instances, no bill. You trade a cold start for it.
- Scales to zero when idle and spins up on demand. You pay per invocation and compute time, not for hours an instance sits waiting.
- deploy_serverless.py
- from sagemaker.serverless import (
- ServerlessInferenceConfig)
- cfg = ServerlessInferenceConfig(
- memory_size_in_mb=2048,   # 1024 to 6144
- max_concurrency=10,       # account default
- )
- predictor = model.deploy(
- serverless_inference_config=cfg,
- endpoint_name="northstar-agent-serverless",
- )
- New account default: 5 serverless endpoints and 10 total concurrency. Non-zero, so no quota request.
- Wins: $0 while idle; no instances to manage
- Costs: cold start of 1–5 s after idle; 6 GB memory cap; 60 s per call; instances win past the crossover (≈200 requests/min here)
- 8
> Notes: QUESTION: How do you serve a model that is busy for a few hours a day and idle the rest, without paying for the idle hours?   Serverless Inference scales to zero when idle and spins up on demand. Compare the cost models: a standard endpoint costs instance price times hours, busy or not. Serverless costs per invocation plus compute time while it runs.   Walk the code. memory_size_in_mb sets memory per invocation, from 1 GB to 6 GB, and CPU scales with it. max_concurrency is concurrent requests, not instances. I set it to 10 because that's the new-account default for total serverless concurrency across the whole account. Twenty, which you'll see in some examples, exceeds what your account starts with. The default quota is 5 serverless endpoints and 10 total concurrency, and unlike ml.m5.large endpoints it isn't zero. Verified on the course's quota sweep.   The chart is illustrative. The instance line is flat at $0.115 an hour whatever the load. The serverless line rises with traffic. Where they cross depends on memory size and how long each invocation runs; at these assumptions it's around 200 requests a minute. A rule of thumb: if the endpoint is idle more than about 30 percent of the time, serverless is likely cheaper.   The costs: cold starts of 1 to 5 seconds after an idle period, a 6 GB memory cap so no large models, a 60-second limit per call, and above the crossover, instances are cheaper.   NorthStar's customer service agent runs on Bedrock, so serverless doesn't apply to it directly. The cost comparison applies to any custom model you host.   Row and box: Serverless is a way to host the box, not a fourth pattern. It fits the synchronous row only when a 1–5 s cold start is acceptable, such as internal tools or low-traffic apps. It rarely fits streaming, where cold starts and the concurrency cap hurt. TRANSITION: Serverless handles idle time. - Async Inference: The Middle Ground
- Accept now, process in the background, deliver the result through S3 and SNS.

> Notes: QUESTION: What do you do when a single prediction takes minutes, or the input is too big for a synchronous call?   Async Inference accepts the request, queues it, processes it in the background, and writes the output to S3. The client either polls S3 or waits for an SNS notification.   Use it for payloads over 6 MB (async accepts up to 1 GB), processing over 60 seconds (async allows up to an hour), SLAs measured in minutes, and expensive requests where queueing smooths the load.   Walk the code.  output_path is where results land.  max_concurrent_invocations_per_instance caps how many requests each instance works on at once; the rest wait in the queue.  notification_config names two SNS topics, one for success and one for errors. deploy still needs an instance type and count; async runs on instances, not serverless capacity.  predict_async returns immediately, and its output_path tells the client where to look.   NorthStar example: if NorthStar deployed a multimodal product-recommendation model and one high-resolution image took 45 seconds, async would be the right pattern.   The timeouts behind this: a SageMaker real-time invocation must finish within 60 seconds, and API Gateway's REST integration timeout defaults to 29 seconds. A two-minute model can't sit behind a synchronous call. Async moves the result out of band through S3 and SNS, so processing time is no longer bounded by a held connection.   Row and box: this slide is the async row’s box. Its hosting knobs are the familiar ones (instance type, count, scaling), except that it scales on queue backlog and can scale to zero instances when the queue is empty. > Notes: QUESTION: Why would you deliberately make an auto-scaler slower at removing capacity than at adding it?  Walk the code top to bottom. register_scalable_target tells Application Auto Scaling which variant it may manage and the bounds. MinCapacity of 1 is a latency decision, not a cost decision: with no warm instance, the next request waits for one to be provisioned, and that takes minutes. MaxCapacity of 2 isn't a design choice. It's your account's endpoint quota. In Lab 5 you'll request two ml.m5.large instances, so two is your ceiling whatever the policy says.  put_scaling_policy uses target tracking on invocations per instance, targeting 1,000 per minute. Those are the Lab 5 values. Now the cooldowns: 60 seconds out, 600 seconds in. If both were short, a spike adds an instance, traffic dips for a moment, the instance is removed, the spike returns, and you've built an oscillator that pays for instances it never uses and hurts latency on every cycle.  Look at the chart. Demand jumps at minute 4. By default the scale-out alarm needs three consecutive one-minute data points, and then the new instance has to be provisioned, so capacity doesn't arrive until around minute 13. For nine minutes the single instance carries 1,800 a minute. On the way down, the scale-in alarm waits for about fifteen minutes of low traffic, so the second instance stays until around minute 38. Fast out, slow in, by design.  The lesson for an architect: auto-scaling handles gradual change. It does not absorb a spike that arrives in seconds. If you know a spike is coming, a product launch or Black Friday, raise MinCapacity on a schedule ahead of time.  TRANSITION: Auto-scaling is for traffic you can't predict. > Notes: Warm floor (MinCapacity=1): at least one instance is always running, so the first request after a quiet period is answered at normal latency. You pay for that instance every hour, including nights and weekends.  Cold start (MinCapacity=0): only possible when the endpoint hosts inference components, and the endpoint config's ManagedInstanceScaling must also set MinInstanceCount=0. Target tracking scales the copy count in to zero when idle. Scaling back out is a separate step-scaling policy, triggered by a CloudWatch alarm on NoCapacityInvocationFailures — SageMaker emits that metric when a request arrives and no copy can serve it. AWS notes provisioning takes several minutes, and invocations fail until it finishes.  Chart: requests start at minute 5. The warm floor serves them immediately. The cold-start endpoint has no capacity until about minute 12, so minutes 5–12 are failed requests. After traffic stops at minute 28, target tracking takes roughly 15 minutes to scale back in to zero. Timings are illustrative.  Rule of thumb: warm floor for anything with a latency SLA or user-facing traffic (Northstar churn-prod). Cold start for dev/staging, internal tools, and bursty or scheduled workloads where clients can retry. If callers can't tolerate errors but you still want zero idle cost, consider asynchronous inference (requests queue instead of failing) or serverless inference.

## Slide 23
- LLM Inference Serving Optimization Techniques
> Notes: QUESTION: Once the weights fit, which techniques let the same GPUs serve more requests, faster, and what does each one cost you? These techniques improve different parts of LLM inference. They can be combined, but their benefits depend on the model, hardware, and workload. For each technique, ask: what changes, what improves, and what must we validate?  Quantization — store values using fewer bits. Quantization reduces the numerical precision of model weights and, optionally, the KV cache. Moving weights from 16-bit to 8-bit representation roughly halves their raw storage requirement, before accounting for additional metadata. That can help a model fit on a smaller GPU or leave more space for concurrent requests. It does not necessarily halve total GPU memory usage or double performance. We must check hardware support and evaluate whether the reduced precision affects output quality.  Model compilation — execute the calculations more efficiently. Compilation prepares an optimized execution plan for the target hardware. It does not retrain the model. Think of the model as a recipe. A compiler reorganizes how the kitchen performs the work: combining compatible steps, choosing efficient equipment, and reducing unnecessary movement. For example, separate GPU operations may repeatedly write intermediate results to memory and read them back. Combining compatible operations—called operator fusion—can avoid some of those transfers. The compiler can also select efficient kernels, which are functions that run on the GPU. Tools such as PyTorch’s torch.compile and NVIDIA TensorRT support these optimizations. The tradeoffs include preparation time, compatibility constraints, and possible recompilation when execution conditions change. We validate outputs as well as performance.  Response caching — reuse the completed answer. If an appropriate answer already exists in the cache, the application can return it without generating another one. For NorthStar, a general question about an unchanged return policy might be reusable. A personalized offer or current refund status requires much more care. An exact text match is not sufficient by itself: the user’s permissions, conversation context, and underlying information must also match. Semantic caching adds another challenge—similar questions do not always have interchangeable answers.  Prefix caching — reuse part of the computation. This differs from response caching. We reuse the intermediate KV representations for an identical prompt prefix, then continue processing the request and generate a new answer. For example, many NorthStar requests may begin with the same long system instructions. Reusing that prefix can reduce repeated prompt processing and improve time to first token. Ordinary KV caching reuses earlier tokens within a generation. This row focuses on reusing shared prefixes across requests. It consumes cache memory, and its benefit depends on how often compatible prefixes recur.  Continuous batching — keep the GPU productively occupied. Requests generate different numbers of tokens and finish at different times. Continuous batching removes completed requests and admits waiting requests between generation steps. This can improve GPU utilization and throughput. However, more active requests need more KV-cache memory, and larger batches can affect latency. Tune concurrency against the application’s response-time targets rather than maximizing batch size alone.  Check for understanding “Two customers have different questions, but their prompts begin with the same system instructions. Which caching technique can help without reusing the same answer?” Prefix caching. It reuses the shared computation while allowing each customer to receive a newly generated response. When evaluating any of these techniques, measure memory use, time to first token, token-generation speed, throughput, cost, and task quality under representative traffic.  One technique not in the table: paged KV-cache management (PagedAttention in vLLM). Instead of reserving each request’s maximum context up front, it allocates the KV cache in fixed-size blocks as the context grows. That is allocation efficiency, not compression, and it lets more requests fit at once. The diagram version is in the appendix. TRANSITION: These techniques speed up one model call. ## Slide 29
- Review: Model/System Deployment, Hosting, Serving
> Notes: These three terms describe related responsibilities: deployment releases a model version, hosting provides the environment where it runs, and serving executes predictions. The numbered columns distinguish these responsibilities; they are not three independent pipeline stages.  Deployment — How does a version go live?Deployment takes an approved model and makes it available in the target environment. We package the model with its dependencies, configure the target, and choose how to introduce the new version. A canary rollout, for example, initially sends a small share of traffic to the new model. Deployment also includes validation and a rollback path if the release causes problems. It happens when we change a model version or its configuration.  Hosting — Where does the model run?Hosting supplies the resources that support execution: CPU or GPU capacity, memory, runtime software, and networking. Those resources might be in the cloud, on premises, or on an edge device. Hosting can be persistent or temporary. A real-time service may keep resources available for incoming requests, while a batch job can acquire resources, process its data, and release them afterward.  Serving — How does it produce predictions?Serving is the actual inference workflow. It accepts input, applies preprocessing, runs the model, and returns or stores the result. Operational concerns include latency, throughput, batching, and error handling. Serving occurs whenever inference runs, whether that means individual requests, scheduled batches, or streaming events.  Walk through the lower diagram.Deployment configures what runs in the hosting environment. Serving operates inside that environment, turning inputs into predictions. These responsibilities overlap in practice, and one managed platform may handle all three. For NorthStar’s churn model, deploying means releasing an approved model version. Hosting means providing the compute and runtime that execute it. Serving means processing customer features and producing churn probabilities. The same model could support immediate predictions or a nightly batch run, with different hosting and deployment choices. Finally, runtime monitoring connects operations back to release decisions. Rising latency may prompt scaling; errors after a release may prompt rollback; declining predictive quality may trigger investigation and retraining. ## Slide 32
- Load Testing AI Endpoints
> Notes: This slide asks a practical question: Can our prediction endpoint handle peak traffic while remaining fast and reliable—and what happens when demand exceeds its capacity? We answer that with a load test. Locust is a Python load-testing tool that simulates users sending requests to an application. We describe what those users do, how often they do it, and how their numbers increase. Locust records response times, request rates, and failures.  Start with the traffic assumptions across the top. Twenty thousand requests per day averages about fourteen requests per minute over twenty-four hours. That average does not tell us the busiest minute. Here, we assume a production peak of thirty-three requests per minute; ideally, we would get that number from traffic measurements. Testing at sixty-six requests per minute checks whether we can handle twice that peak. Then we push further to discover bottlenecks. The seventy-request reference is specific to this example, not a universal scaling threshold.  First, make the simulated traffic realistic. For our churn prediction service, send a representative mix of customer records. Include normal authentication and realistic bursts. Locust’s simulated user count is not the same as requests per minute. Each user sends a request, waits for the response, and pauses before sending another. If the service slows down, those users may generate fewer requests. We therefore report the load actually achieved, alongside the load we intended to generate.  Second, measure speed and correctness separately. Errors include failed HTTP requests, timeouts, and responses that do not contain valid predictions. Latency measures how long responses take. The p99 is the response time at or below which approximately ninety-nine percent of measured requests finish. A p99 target of two hundred milliseconds focuses attention on the slow end of the experience, rather than just the average. A successful response that arrives late is a latency violation. Keep that separate from request failures so we can tell whether the service is slow, unreliable, or both.  The two charts illustrate those separate outcomes. The upper chart shows response time as traffic increases. The lower chart shows the percentage of requests that fail. The red curves represent a single instance becoming overloaded. The blue curves illustrate how additional capacity might help. These are conceptual curves, not measured benchmark results. Two hundred milliseconds and one percent are example targets that must be chosen for the application.  Third, test the scaling process itself. Autoscaling takes time. The system must detect demand, decide to scale, provision capacity, and become ready to serve traffic. Record both when scaling is requested and when the new capacity starts handling requests. Also track instance count and resource utilization. A scaling policy may use requests per instance, so its target is not necessarily the total request rate shown on the chart. Hold each load level long enough to observe behavior, and repeat the test. At low request volumes, a short run provides very few observations in the slowest one percent, making p99 estimates unstable.  Finally, this example is a fast churn prediction endpoint. For an LLM, we would also measure input and output token lengths, time to first token, and generation speed. For an agent, we would measure total task duration and successful completion.  The goal is to identify the traffic level we can support within our targets—and verify that scaling and recovery work when demand changes.

## Slide 33
- Improving LLM Serving Efficiency
> Notes: This slide separates three complementary techniques for improving LLM serving efficiency. Each addresses a different problem: keeping the GPU busy, reducing the memory needed to store values, and allocating KV-cache memory efficiently.  Continuous batching LLMs generate responses over multiple steps, and requests finish at different times. Continuous batching lets completed requests leave and waiting requests join between generation steps. We do not have to wait for an entire group to finish before admitting more work. This improves GPU utilization and can increase throughput. However, more active requests also require more KV-cache memory. We must balance throughput against response time, including time to first token and the delay between generated tokens.  Quantization Quantization stores values using fewer bits—for example, moving model weights from 16-bit floating point to 8-bit or 4-bit representations. Smaller weights leave more memory available for the KV cache and other runtime needs. Some systems also support quantizing the KV cache. The slide’s phrase “KV cache optional” means that quantizing the cache is optional, not that the cache itself is unnecessary. Memory savings do not guarantee a proportional speedup. Results depend on hardware support, inference kernels, and the workload. We also need to evaluate output quality on representative tasks.  Paged KV-cache management PagedAttention addresses how cache memory is allocated. Instead of reserving one large contiguous region for each request, the serving engine allocates fixed-size blocks as the request’s context grows. The blocks belonging to one request do not have to sit next to one another. This reduces unused reservation and fragmentation. It does not inherently compress the cached values or reduce the information needed for each token.  Walk through the diagrams Each color represents one request. Both diagrams contain exactly the same useful cached data: three blue blocks, four green, two red, and three yellow. On the left, each request has a reserved region. The gray blocks are currently unused, but unavailable to other requests under this allocation scheme. On the right, the useful data occupies blocks from a shared pool. The pale-gray blocks remain available for growing contexts or additional requests. The improvement comes from allocating memory more efficiently—not from shrinking the colored data.  Implementation choices vLLM is a serving engine that brings these techniques together. When operating it ourselves, we configure the runtime and manage the resources supporting it.  With Amazon Bedrock, AWS manages the model-serving infrastructure. We give up some control over GPU selection and runtime tuning in exchange for less operational work. We still manage application demand, quotas, costs, and performance expectations.  Check for understanding “If model weights fit on the GPU, but requests waste memory by reserving their maximum context length, which technique most directly addresses that problem?” Paged KV-cache management. Quantization reduces the size of stored values; continuous batching improves scheduling; paged allocation reduces wasted cache reservation.
