## Slide 4
> Notes: This slide introduces the first of our major ingestion patterns: batch ingestion. The defining idea is straightforward: rather than processing every data event immediately as it occurs, we accumulate data over some period of time and process it together on a schedule. That schedule might be every few minutes, hourly, nightly, or even weekly. What makes it “batch” is not a particular amount of time—it is that we’re collecting multiple records and processing them as a group. Common Data Sources Look at the sources on the left. Batch ingestion works naturally with data that already exists in persistent storage. That could be CSV or other files in Amazon S3, records extracted periodically from a relational database such as Amazon RDS, data accumulated in a data lake, or files coming from an organization’s existing on-premises systems. Imagine that we operate an e-commerce company. Throughout the day, customers place orders and the transactional system records those orders in a database. Our machine-learning system may not need every transaction the instant it occurs. Instead, every night we could extract all transactions that occurred during the previous day and load them into our analytics environment. That’s a classic batch-ingestion workload. How Batch Processing Works The timeline in the center illustrates the key concept. Notice the small vertical lines. Think of these as individual data events arriving continuously. But we’re not necessarily processing each event when it arrives. Instead, at predetermined intervals, the pipeline collects the accumulated records and processes them as a batch. The blue rectangles represent those processing windows or jobs. For example, suppose we run an ingestion job every six hours: At noon, process everything that arrived since 6:00 a.m.At 6:00 p.m., process everything that arrived since noon.At midnight, process everything that arrived since 6:00 p.m. This gives us a very predictable operational model. Latency Is a Design Choice The tradeoff is latency.  If we run the pipeline once per day, a record arriving just after today’s job might wait almost 24 hours before being processed. If we run every hour, the maximum delay becomes much smaller—but now we’re executing and managing 24 jobs per day instead of one. So the question isn’t: “How do we eliminate latency?” The better engineering question is: “How fresh does the data actually need to be for this business problem?” If I’m detecting a fraudulent credit-card transaction, waiting until tomorrow is probably unacceptable. But if I’m retraining a customer-churn model once per week, having data that is several hours old may make essentially no difference. That distinction matters because freshness has a cost. Typical Use Cases Batch ingestion is particularly appropriate for historical data loads and backfills. Suppose we’ve just built a new feature and want to calculate it for the previous three years of customer activity. That’s inherently a batch problem—we already have the historical data and want to process a large volume efficiently. It’s also common for periodic reporting. A financial report generated every morning doesn’t necessarily require second-by-second ingestion throughout the night. And batch processing is extremely common when creating model-training datasets. If we’re training a model on 100 million historical observations, we generally don’t want to process those records individually as real-time events. We want an efficient, scalable process capable of transforming large volumes of data together. Why Batch Remains Important It’s easy to assume that streaming is somehow more advanced and therefore always preferable. That’s the wrong architectural conclusion. Batch ingestion is often simpler to develop, easier to operate, easier to debug, and less expensive than an equivalent real-time architecture. Suppose our business requirement says: “The model must be retrained every Sunday using all transactions through Saturday.” A complex streaming architecture doesn’t necessarily provide additional business value. A scheduled batch pipeline may satisfy the requirement perfectly while dramatically reducing operational complexity. This is a recurring principle in cloud architecture: Don’t optimize the architecture for the fastest technically possible response. Optimize it for the response time the business actually requires. In-Depth Use Case — Nightly Customer Churn Features Consider a telecommunications company predicting which customers are likely to cancel service. During the day, several operational systems generate data: billing transactions, customer-support interactions, service usage, account changes. At 1:00 a.m., an AWS pipeline could extract the previous day’s records, place them in Amazon S3, use AWS Glue to clean and transform the data, and calculate features such as: number of support calls in the last 30 days,days since the last payment,change in monthly usage,number of recent service interruptions. Those features could then be written to a feature store and used by the next model-training job. Notice that nothing about this use case inherently requires millisecond processing. If the business takes retention actions once each morning, a nightly batch pipeline is entirely consistent with the business requirement. Key Takeaway The statement at the bottom captures the central tradeoff: Batch ingestion trades real-time freshness for operational simplicity, scalability, and cost efficiency. When evaluating an ingestion architecture, start by asking: What decision will this data support, and how quickly must that decision be made? If the answer is measured in hours rather than seconds, batch ingestion should probably be one of the first architectures we consider.

## Slide 9
- End-to-end AI/ML Data Pipeline
> Notes: The figure depicts an end-to-end data pipeline for AI/ML systems, showing how data moves from its original sources through ingestion, validation, transformation, feature preparation, model inference, and finally monitoring and lineage. The key idea is the arrow at the bottom: “Data Flow (Ingestion to Prediction)”. Data moves progressively from relatively unstructured/raw information on the left to model-ready information and predictions on the right.  The 8 stages 1. Source Systems Where data originates Internal databases, third-party APIs, log files, user-generated content  2. Ingestion Layer Move data into the platform Batch, streaming, and event-driven ingestion using technologies such as Airflow, Spark, Kafka, or Lambda  3. Raw / Landing Zone (Immutable) Preserve the original data Incoming data is stored unchanged in a data lake/cloud storage such as S3 or ADLS  4. Validation Gate Stop bad data before it spreads Data-quality checks and schema enforcement; tools such as Great Expectations or Soda  5. Cleaned/Enriched Zone Turn raw data into trustworthy, usable data Cleaning, transformations, deduplication, joins, and enrichment; e.g., dbt or Spark  6. Feature/Document/Embedding Layer Prepare data specifically for AI/ML Feature engineering, document processing, and embedding generation  7. Model Inference Generate predictions Batch inference or online/real-time inference using systems such as SageMaker or Triton  8. Monitoring/Lineage Observe and trace the system Track where data came from, model artifacts, experiments, and operational behavior (better envisioned as stretching across all stages).   Why the Raw Zone is “immutable” Stage 3 is particularly important. Suppose an organization receives 10 million customer transactions. Rather than immediately cleaning and overwriting them, it first stores an untouched copy. That gives you something like:  Original data → Raw copy → Processing → Cleaned data If a transformation turns out to contain a bug six months later, you can go back to the original data and rebuild the downstream datasets. The lock symbol in the diagram represents this principle.  Why there is a Validation Gate Stage 4 acts as a quality firewall. Imagine an upstream system normally sends: customer_age = 42 but suddenly starts sending: customer_age = "unknown" or a required customer_id field disappears. Without validation, corrupted or incompatible data can propagate into analytical tables, features, embeddings, and ultimately model predictions. The validation gate checks things such as schema, types, ranges, missing values, uniqueness, and business rules before allowing the data to continue. So the pipeline isn’t simply: ingest → transform It deliberately introduces: ingest → validate → transform That separation is an important architectural principle.  Stage 5 creates the trustworthy data foundation After validation, the data is transformed into a form that applications and models can actually use. For example, three datasets might contain: Customerscustomer_id, name, location Transactionscustomer_id, product_id, amount Productsproduct_id, category, price Stage 5 could clean duplicates, standardize locations, join the datasets, and append customer profiles. The result might become: customer_id → demographics + purchases + product history That enriched dataset can now feed many downstream applications.  Stage 6 is where the architecture becomes explicitly AI-oriented This is arguably the most interesting box because it supports both traditional machine learning and generative AI. For conventional ML, the pipeline might create features: transactions → spending history → avg_purchase_30_days For generative AI/RAG, it might process documents: PDF → extract text → chunk documents → generate embeddings Those embeddings could then be stored in a vector-capable system for retrieval. So Stage 6 effectively represents several possible AI preparation pipelines: Structured data → features → ML model and Documents → chunks → embeddings → vector retrieval → LLM This is why the box is labeled “Feature/Document/Embedding Layer” rather than simply “Feature Store.”  Stage 7: Model Inference The prepared information now reaches a deployed model. The diagram distinguishes two important inference patterns. 1. Batch inference processes many records together. For example, every night: Score all 5 million customers for churn probability. The predictions might be written back to a database or object store. 2. Online inference produces predictions when an application requests them: Customer opens application → API request → model → prediction → response This typically requires much lower latency.  Stage 8: Monitoring and Lineage The last stage answers questions such as: Where did this prediction’s data come from? Which dataset version was used? Which model generated the prediction? Which model parameters were deployed? Has model behavior changed? Are production services healthy?  One subtle point is that Stage 8 shouldn’t really be interpreted as happening only after Stage 7. In a real architecture, monitoring, metadata, governance, and lineage typically span much of the entire pipeline: Sources → Raw → Ingestion → Validation → Clean → Features → Model──────────────── Monitoring/lineage ────────────────  Visually, it appears as the final box, but architecturally it is often cross-cutting.  A concrete example Consider an AI system that predicts customer churn. 1 — Sources: CRM records, transactions, website logs, customer-support conversations. 2 — Raw Zone: Preserve all incoming records exactly as received. 3 — Ingestion: Nightly transaction files arrive through batch pipelines while website events stream through Kafka. 4 — Validation: Verify customer IDs, timestamps, schemas, transaction amounts, and required fields. 5 — Clean/Enrich: Remove duplicates, combine transactions with customer profiles, calculate account histories, and normalize fields. 6 — Feature/Embedding: Calculate features such as purchase frequency and days since last purchase. Customer-support conversations could also be converted into embeddings or other derived signals. 7 — Inference: A deployed churn model calculates something such as: Customer 3812 → churn probability = 0.81 8 — Monitoring/Lineage: Track the model version, feature/data versions, prediction behavior, service latency, and the provenance of the data that contributed to the result.  The deeper architectural message The diagram emphasizes that production AI is much more than the model. The actual model appears in only one relatively small portion of the architecture. Most of the system is concerned with getting reliable, reproducible, governed, model-ready data to that model: Raw Data↓Reliable Data↓AI-Ready Data↓Model↓Prediction↓Monitoring   That distinction matters when teaching large-scale AI systems: the model is a component of the production system, not the production system itself.

## Slide 12
- Data Contracts: What are they and why they Matter
> Notes: What problem are data contracts solving? “Up to this point, we’ve talked about moving data through a pipeline and validating it. But there’s a deeper organizational problem: what happens when one team produces data that another team depends on? The producer may change that data without realizing what it will do downstream. A data contract addresses that problem. Think of it as being similar to an API contract for data. It turns an informal dependency between teams into an explicit, versioned, testable agreement.”  Walk through the producer → contract → consumer model “On the left we have the data producer. This might be a transaction service, CRM system, mobile application, or another pipeline. The producer owns the data and publishes it for downstream use.  On the right is the data consumer. That could be an analytics system, a feature-engineering pipeline, or an ML model. The important point is that the consumer is building something that depends upon assumptions about the producer’s data. The data contract in the middle makes those assumptions explicit.”  What does the contract actually specify? “There are six things I want you to notice. Schema answers: What does the data look like? What fields exist? What are their types? Which are required? Semantics answers a different question: What does the data mean? What are the units? What exactly does customer_id represent? What does revenue mean? That distinction is important. Data can be perfectly valid according to its schema and still be semantically wrong. Quality establishes rules such as completeness, uniqueness, allowed values, and validity. Freshness and SLA establish operational expectations. For example, perhaps the dataset must be available within two hours of the source transaction. Ownership tells us who is responsible for the dataset and who depends on it. And finally, evolution specifies how changes are made and versioned.”  A concrete failure example “Here’s a simple example of why semantics matters. Suppose a transaction system produces: amount = 49.95 and everyone understands that amount means dollars.  An upstream team changes the system so that amounts are now represented in cents: amount = 4995 The pipeline might continue running. The field still exists. It is still numeric. Nothing necessarily crashes. But imagine a feature-engineering pipeline calculating average customer spending. Suddenly a $49.95 transaction looks like $4,995. That’s potentially more dangerous than a pipeline crashing because we’re now producing incorrect data successfully. A good data contract makes the unit and meaning part of the agreement.”  Contrast the bottom two boxes “That brings us to the bottom of the slide.  Without a data contract, problems tend to be discovered downstream. The producer makes a change. The pipeline continues. Eventually an analytics dashboard looks strange, a feature changes distribution, or a model’s performance deteriorates. Now several teams have to work backward to discover what changed.  With a contract, we’re trying to detect the incompatibility much closer to where it originated. A proposed producer change can be checked automatically against the contract before it reaches production.” You can characterize this as: Without contracts: detect failure downstream.With contracts: detect incompatibility upstream.  Connect this to the Validation Gate “Notice how this connects to the pipeline architecture we discussed earlier.  A data contract and a data-quality test are not the same thing.  The contract defines the promise. The validation system checks whether the promise is being kept. For example, the contract might say: customer_id must never be null. Our validation gate—perhaps implemented with AWS Glue Data Quality service—actually tests incoming data to determine whether that requirement has been satisfied.  So: Contract = expectationValidation = enforcement  That’s an important distinction.” Connect it to ML “For machine learning, data contracts become particularly important because ML systems can fail silently. Suppose our model was trained using a feature called annual_income. Originally that means: gross household income. The upstream producer later changes its meaning to: individual taxable income. The column name hasn’t changed. The datatype hasn’t changed. The pipeline doesn’t crash. But the statistical meaning of one of our model features has changed. That can lead to: semantic change → feature distribution change → model degradation → business impact. A contract gives us a mechanism for declaring that semantic change to be a breaking change rather than allowing it to silently propagate.”  Explain why versioning matters “This is also why the word versioned in our definition matters. Not every change should break consumers. Adding an optional field might be backward-compatible and result in something like: v1.0 → v1.1 Changing the meaning of an existing field, removing a required field, or changing units may be a breaking change: v1.x → v2.0 The important principle isn’t the exact numbering convention. It’s that changes to shared data should be managed rather than surprising consumers.”  Close with the takeaway “The sentence at the bottom is the idea I want you to remember: A data contract turns an implicit dependency into an explicit, testable agreement. And that changes the way we think about data reliability. We’re no longer saying, ‘Here’s some data; hopefully it continues looking the same.’ We’re saying: ‘Here is the data we provide, here is precisely what it means, here are the quality and operational guarantees we make, and here is how we’ll manage changes.’ That is what allows independent producer and consumer teams to build reliable systems on top of shared data.”  Transition to the next slide “The natural next question is: What does one of these contracts actually look like? On the next slide, we’ll open one up and examine its schema, semantics, quality rules, SLA, ownership, versioning, and enforcement—and then distinguish a backward-compatible change from a breaking change.”

## Slide 13
- Anatomy of a data Contract
> Notes: This slide is the natural follow-on to the previous “Why Data Contracts Matter” slide. The previous slide establishes the concept; this one opens up the contract and shows students what is actually inside one. These notes should support about 5–7 minutes of presentation.  Opening: From concept to implementation “On the previous slide, we defined a data contract as a formal, versioned agreement between a data producer and its consumers. Now let’s make that concrete. On the left is an example contract written in YAML. YAML isn’t essential—the contract could be represented in JSON or another machine-readable format. What’s important is that the agreement isn’t buried in a Word document or someone’s institutional knowledge. We want it represented in a form that both humans and automated systems can understand. There are seven components here that I want you to recognize.”  1. Schema — What does the data look like? “The first component is the schema. Schema describes the structural characteristics of the dataset: What fields exist? What datatype does each field have? Which fields are required? What format is the dataset delivered in? For example, our contract says we expect fields such as event_id, customer_id, product_category, and event_timestamp.  This is the most familiar part of a data contract, but schema alone is not enough.” A useful question to ask the class: “If revenue is defined as a decimal, do we actually know what revenue means?” The answer is no—which leads to semantics. 2. Semantics — What does the data mean? “Semantics describes the business meaning of the data. Suppose a field is: product_category: string Schema tells us it’s text. Semantics tells us things like: The value must correspond to our official product catalog. Likewise: event_timestamp might mean: The UTC timestamp at which the customer event occurred. That’s much stronger than simply saying it’s a datetime. This is particularly important for ML because a field can remain structurally valid while its meaning changes.” I would remind students of the previous example: “If amount changes from dollars to cents, the schema may still validate. The semantics have changed.” 3. Quality — How good must the data be? “The third component specifies quality guarantees. Notice that these aren’t vague statements like ‘the data should be good.’ They’re measurable. For example: Completeness: perhaps 99.5% or more of records must contain a value. Uniqueness: event_id must be 100% unique.  Validity: product_category must belong to an approved set.  We could also specify ranges, regular expressions, referential integrity, or other business rules. The key idea is that we’re converting an expectation into something testable.” Then reinforce the distinction from the previous slide: The contract specifies the rule. ## Slide 14
- Feature Engineering Principles
> Notes: Feature Engineering Principles  Opening “Feature engineering is the process of transforming the data we have into representations that make the underlying patterns easier for a model to learn. The important distinction on this slide is between raw fields and engineered features. Raw data describes what happened; features represent that information in a form designed for prediction.”  Start with the raw inputs “On the left are fields we might receive from a transaction system: transaction_date, amount_usd, merchant_id, customer_id, and country. These fields are useful, but they don’t necessarily expose the behavioral patterns our model needs. For example, knowing that a transaction occurred for $75 tells us something. Knowing that $75 is three times this customer’s normal transaction amount may tell us much more.” 1. Aggregation — summarize behavior “The first technique is aggregation. Rather than considering transactions independently, we calculate statistics over a group or time window. For example: What is this customer’s average transaction amount over the previous 30 days? That produces: avg_amount_30d We might similarly calculate: txn_count_7dtotal_spend_30dmax_amount_24h These features convert individual events into behavioral history.” A useful point to emphasize: “The raw field tells us what happened. The aggregate feature gives us context about what normally happens.” 2. Normalization — put numeric values on useful scales “Next is normalization or standardization.  Numeric variables can have dramatically different scales. Transaction amount might range into thousands of dollars while another feature ranges between zero and one. One common transformation is the z-score shown here: z=\frac{x-\mu}{\sigma} We subtract the mean and divide by the standard deviation. Instead of simply knowing that a transaction was $500, we can represent how unusual that value is relative to some reference distribution.” I’d add one caution: “Not every model requires normalization. Tree-based models, for example, are generally much less sensitive to feature scale than distance- or gradient-sensitive methods. Feature engineering should be driven by the model and problem rather than applied mechanically.”  3. Encoding — convert categories into model representations “The third example is encoding. Models generally need some numerical representation of categorical information. Suppose: country = "US" We could create: country_US = 1 and otherwise set it to zero. That’s the basic idea behind one-hot encoding. Other situations may call for ordinal encoding, frequency encoding, target encoding, hashing, or—in modern AI systems—learned embeddings. The right representation depends on the cardinality and meaning of the variable.” Engineered features “Now look at the right side. We’ve transformed relatively simple source fields into features such as: avg_amount_30damount_normcountry_USdays_since_last_txntxn_count_7d Notice something important: some of the best features don’t correspond to any single column in the source system. For example: days_since_last_txn requires combining customer identity, transaction history, and time. That’s the essence of feature engineering—we’re introducing useful representations of the underlying phenomenon we’re trying to predict.” A concrete example: fraud detection “Imagine we’re predicting whether the current transaction is fraudulent. A raw transaction tells us: Customer 827 spent $850 at 2:13 AM. But engineered features might tell us: Average transaction over 30 days = $64Current transaction = 5.2 standard deviations above normalTransactions in previous 7 days = 3Days since last transaction = 12Country differs from customer’s normal country Those contextual features may be much more predictive than $850 alone.” The most important warning: leakage “One of the biggest dangers in feature engineering is data leakage. Suppose we’re predicting fraud at 2:13 PM. Our feature: avg_amount_30d must be calculated using information available before 2:13 PM. We cannot accidentally include transactions that occur afterward. Otherwise, we’re allowing the model to learn from the future.”  Put simply: A feature used to make a prediction at time T must be computable using information available at time T. “This is especially important with rolling windows and aggregations.” Connect to the previous slides “This also shows why our earlier discussion of data contracts matters. Suppose amount_usd suddenly changes from dollars to cents. Our feature pipeline might continue running successfully—but: avg_amount_30d and amount_norm could suddenly change dramatically.  So there is a dependency chain: Data contract → validated source data → feature engineering → model Bad upstream data becomes bad features, and bad features become bad predictions.” Training-serving consistency “There’s another production issue we’ll encounter later. We need the feature calculated during model training to mean exactly the same thing as the feature calculated during inference.  If training defines: avg_amount_30d one way, but production computes it differently, we create training-serving skew. That’s one of the motivations for standardized feature pipelines and feature stores.” Closing takeaway “The main point of this slide is that feature engineering is not simply changing column formats.  We’re trying to transform: raw observations → useful representations of behavior and context. Aggregation captures history.Normalization captures relative scale.Encoding represents categories.Derived features capture relationships and context. And throughout that process we have to preserve semantic correctness, point-in-time correctness, and consistency between training and inference.  Those three properties are just as important as the feature transformation itself.”   Feature Engineering: Transforming Raw Data into Model Inputs  Principle 1: Features should encode information the model can't learn itself Don't give the model raw timestamps; give it derived temporal features (day_of_week, days_since_last_purchase, is_holiday_period) Don't give it raw dollar amounts; give it relative values (spend_vs_avg, basket_size_percentile)  Principle 2: Features must be computable at inference time If a feature requires data that won't be available when the model makes a real prediction, it will cause training/serving skew NorthStar example: using "days until customer's next purchase" as a feature — unknowable at inference time  Principle 3: Features should be stable under distribution shift Absolute counts degrade as the customer base grows; ratios and percentiles are more stable NorthStar example: transactions_last_30d is less stable than transactions_last_30d / avg_transactions_30d_cohort  NorthStar Feature Examples:| Feature | Type | Engineering ||---------|------|-------------|| tenure_days | Raw | Days since first purchase || spend_30d | Aggregation | Sum of transaction amounts, last 30 days || recency_score | Derived | Days since last purchase, normalized 0-1 || loyalty_tier | Encoded | Ordinal encoding: Bronze=1, Silver=2, Gold=3 || avg_basket_trend | Time-series | Ratio: avg_basket_90d / avg_basket_180d |  Notes: "Feature engineering is where domain knowledge becomes model signal. The NorthStar churn model isn't predicting from raw data — it's predicting from engineered signals about customer behavior over time. The quality of those features matters more than the sophistication of the model." Classic lesson: "A simple logistic regression with good features almost always outperforms a complex deep learning model with raw data."

> Notes: Presentation Notes — SageMaker Feature Store: Online and Offline Paths Opening “This slide addresses a fundamental production-ML problem: the model needs the same definition of a feature when we train it and when we use it to make predictions. > Notes: Presentation Notes — SageMaker Feature Store: Online and Offline Paths Opening “This slide addresses a fundamental production-ML problem: the model needs the same definition of a feature when we train it and when we use it to make predictions.
