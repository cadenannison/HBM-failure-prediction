> Notes: Speaker notes — approximately 10–12 minutes  Opening: How to read this map “AI security extends across the entire system—from the data we collect to the actions an application takes. A secure model alone does not make a secure AI system. This figure organizes that security surface into four connected domains: data security, API and application security, infrastructure security, and model security. Within each domain, the left column identifies the assets we need to protect, and the right column identifies threats to those assets. The arrows illustrate how a compromise in one domain can affect another. They are examples of attack paths, not an exhaustive list or a sequence that every attack follows. One clarification about the labels: some threats shown here, such as credential theft and misconfigured access, are familiar cybersecurity problems. AI introduces additional assets, attack paths, and consequences that make those existing problems especially important.”  1. Data security — upper left “Start with the data. AI systems depend on more than training datasets. They also use retrieval documents, inference inputs, generated outputs, and logs. Each can contain sensitive information or become a route for manipulating the system. For NorthStar, these assets include customer records used to train the churn model, documents retrieved by the offer-generation system, customer messages submitted to the service agent, and logs recording the agent’s interactions.  The first threat is data and corpus poisoning. Training-data poisoning changes the examples or labels used to learn a model. An attacker might alter churn labels so that the model learns a misleading relationship. Retrieval-corpus poisoning works differently. An attacker inserts or modifies documents that a RAG system retrieves. The model’s weights may remain unchanged, but its answers can still be manipulated because it receives corrupted evidence.  The second item, PII in training sets, is a sensitive-data exposure risk. PII means personally identifiable information. Its presence is not itself an attack, but it creates information that could be disclosed through unauthorized access or model behavior. We should ask whether each sensitive field is necessary and how its use is controlled.  The third threat is exfiltration through third-party APIs. Sensitive information can leave the system when an application or agent sends it to an external service. That information might appear in a tool argument, generated output, or outbound request. Logs deserve particular attention. Teams often protect the original dataset while allowing prompts, retrieved passages, and tool responses to accumulate in broadly accessible logs.”  Controls to emphasize: Track data provenance and restrict who can modify datasets and retrieval documents. Minimize sensitive data and apply access controls to retrieval results. Review what information can leave through external APIs. Protect and redact logs as carefully as other sensitive datasets.  Transition: “Protecting stored data is only part of the problem. We also need to control how the application interprets and acts on that data.”  2. API and application security — upper right “This domain includes inference endpoints, agent interfaces, and tool calls—the places where users and other systems interact with AI.  Prompt injection occurs when attacker-controlled content attempts to redirect the model’s behavior. The instruction may arrive directly in a user message or indirectly inside retrieved content. For example, a retrieved document might tell the model to ignore its task and disclose customer information.  Jailbreaking focuses on bypassing a model’s safety restrictions. These concepts overlap, but it helps to distinguish overriding an application’s intended instructions from evading the model’s safety boundaries. Neither problem is solved by writing a stronger system prompt alone.” OWASP Gen AI Security Project  “Excessive agency means the system has more functionality, permissions, or autonomy than its task requires. A NorthStar agent that explains a refund policy has limited authority. An agent that can issue unrestricted refunds presents a much larger exposure. Enforce authorization in application code and tool services, with approval requirements for consequential actions.” OWASP Gen AI Security Project  “Improper output handling occurs when downstream software trusts model output without appropriate validation. Generated SQL, HTML, or tool arguments need checks suited to where they will be used.  Unbounded consumption concerns requests or agent behavior that consume excessive resources. Long outputs, repeated tool calls, and recursive loops can produce service disruption or runaway costs. Apply request quotas, token budgets, timeouts, and limits on tool execution.” OWASP DevSecOps Guideline  Teaching emphasis: “A model can propose an action. The surrounding software must decide whether that action is authorized.”  3. Model security — lower right “Model security protects the model itself: its weights, architecture where proprietary, and learned behavior. Several terms in this box sound similar, but they ask different questions: Model extraction: Can an attacker obtain or reproduce the model’s functionality, for example by systematically querying it to train a substitute? Training-data extraction: Can an attacker recover actual training content that the model has memorized? Model inversion: Can an attacker reconstruct information or representative characteristics associated with the training data? This does not necessarily recover an exact original record. Membership inference: Can an attacker determine whether a particular record was included in training? The distinction is between copying the model, recovering training content, reconstructing information, and detecting participation in the training set.” nvlpubs.nist.gov “Adversarial inputs are deliberately constructed to cause unintended model behavior. In a traditional classifier, that might mean manipulating an input so that it is misclassified. In an LLM application, an attacker may use instructions designed to redirect the model. The overlap with the application-security box is intentional: an attack enters through an interface and affects model behavior.” National Cyber Security Centre “For NorthStar, imagine an attacker repeatedly querying the churn endpoint to approximate its decision function. That illustrates model extraction. Asking whether a specific customer’s record contributed to training illustrates membership inference. When discussing defenses, distinguish protecting the model artifact from protecting access to its predictions. Restricting access to weight files addresses a different exposure from monitoring suspicious patterns of API queries.”  4. Infrastructure security — lower left “The infrastructure domain supports everything else. It includes compute, storage, networking, identity and access management, and the software supply chain.  Credential theft can give an attacker access to training data, model artifacts, or deployment systems. The damage depends heavily on the permissions attached to those credentials.  Misconfigured access includes overly broad storage permissions, exposed endpoints, and service identities with unnecessary privileges.  Compromised dependencies create another route into the system. Training and serving environments rely on libraries, containers, packages, and build tools. A malicious component can affect the system before a model ever receives a user request.  The last item combines two related but distinct concerns. A backdoored model can behave normally until a particular trigger activates malicious behavior. A malicious model file may exploit an unsafe loading mechanism to execute code. Evaluating a model’s prediction quality does not establish that its file is safe to load.  For NorthStar, think about the identities used by data pipelines, training jobs, deployment automation, and agent tools. Each identity should have only the permissions its job requires.”  Controls to emphasize: Use narrowly scoped identities and protect credentials. Restrict network and storage access. Verify the provenance and integrity of dependencies and model artifacts. Separate development, training, and production permissions.  5. Explain the arrows — attacks cross domain boundaries “Now look at the purple arrows. These connections are the main reason to present security as a map.  The top arrow says ‘Corpus poisoning reaches app layer.’ An attacker changes a document in the retrieval corpus. The application retrieves it, and the model uses it as context. Corrupted evidence can produce a misleading answer; embedded instructions can also attempt to redirect application behavior.  The downward arrow says ‘Adversarial inputs target model.’ An attack enters through an endpoint or agent interface, then attempts to alter the model’s response.  The bottom arrow says ‘Supply chain compromises model.’ An untrusted dependency, training component, or model artifact can introduce a compromise that appears later as malicious model behavior.  These arrows also show why ownership matters. The data team, application team, platform team, and model team each control part of the defense. Security reviews need to examine the connections between their systems.”  6. Walk through one NorthStar example “Suppose an attacker places a malicious document in NorthStar’s customer-service knowledge base. The document contains instructions telling the agent to send customer details to an external URL.  First, that is a data-security problem: unauthorized content entered the retrieval corpus.  Second, it becomes an application-security problem if the agent treats those retrieved instructions as commands.  Third, the attempted disclosure depends on tool authority and infrastructure permissions. Can the agent make arbitrary outbound requests? Can it access the customer details? Does the tool service enforce what may be sent and where?  This example gives us several opportunities to interrupt the attack: control document ingestion, enforce retrieval permissions, limit tool capabilities, and restrict outbound destinations. The design should remain protective even if the model follows a malicious instruction.”  Discussion prompt “Suppose we improve the system prompt, but the agent still has unrestricted access to customer records and an unrestricted HTTP tool. How could an attacker reach them? Where could a compromise spread? Which controls interrupt that path? Apply those questions to the complete production system, including its data, interfaces, tools, model artifacts, and infrastructure.”

## Slide 5
- Threat Profile Comparison Across AI System Types
- Language models receive instructions and data in the same form: natural language.
> Notes: What new security threats does each type of AI system add, and why does the damage potential grow as we move from traditional ML to agents?  Read this slide from left to right, and notice the plus signs between the columns. Each system type keeps every threat from the one before it and adds a new layer.  Start with traditional ML. There are two threat surfaces. The first is the data: an attacker can poison the training set, or sensitive training records can leak. The second is the model: an attacker can extract it by querying it repeatedly, craft adversarial inputs to fool it, or use inversion and membership inference to work out what data it was trained on. If any of these attacks succeeds, the worst case is wrong outputs. That’s bad, but the impact is contained.  LLM-based systems keep all of those threats and add the interaction layer: prompt injection and jailbreaks. The red line at the bottom explains why this layer exists. A language model receives instructions and data in the same form, natural language, and it has no reliable way to tell them apart. A sentence buried in a retrieved document or an email can act like a command. So the impact grows from wrong outputs to wrong outputs plus leaks, such as the system prompt, private context, or other users’ data.  Agent-based systems add the action layer: tool misuse and over-broad permissions. This is the big jump. An agent doesn’t just say things, it does things. It sends email, runs code, calls APIs and modifies records. When a prompt injection hits an agent, the attacker isn’t just getting a bad answer. The agent takes real actions for them, using the agent’s own credentials. That’s why the blast radius bar runs from narrower to widest. The takeaway on the right is the design principle to remember: the more permissions an agent holds, the larger its blast radius. You can’t make a model immune to injection, but you can limit what a compromised agent is able to do.

> Notes: If we can't stop prompt injection, how do we build agents that are safe anyway?  On the last few slides we saw that language models receive instructions and data through the same channel. There is no patch for prompt injection the way there is for SQL injection. Any web page, email or product review the model reads can carry a sentence that tries to take control, and attackers rephrase, encode or translate their way past filters. So this slide flips the question. Instead of "how do we stop every injection?", we ask: "when one gets through, what can it actually do?"  Simon Willison gave us a useful way to see this, which he calls the lethal trifecta. An agent becomes a data-theft machine when it combines three things: it reads content from people you don't trust, it can reach private data, and it can send information out. Picture a new employee who opens mail from strangers, holds the keys to the records room, and can ship packages. One forged letter asking for the customer files is all it takes. Remove any one of the three and the con fails.  Meta's security team turned that into a design rule, the Agents Rule of Two, and that is the triangle on the left. Each corner is one property: processing untrusted input; accessing sensitive data or systems; and changing state or communicating externally. Notice Meta widened Willison's third leg from "can send data out" to "can change things in the world", because deleting records or placing orders is dangerous too. The rule: within one session, meaning one run of the agent with everything it has read and everything it can touch, an agent may hold at most two of the three. Each edge of the triangle is an allowed pair. If a task genuinely needs all three, the red center, a human approves the risky step, or you split the work into separate sessions with separate context and permissions.  Read the pill at the bottom carefully: two of three blocks the worst case, not all risk. An agent that reads untrusted input and can change state could still be tricked into deleting something, even with no private data involved. Meta says this itself: the Rule of Two supplements least privilege; it does not replace it.  The right side is how we put this into practice, and it comes in two groups.  The first group contains damage. These controls work even when the injection succeeds.  One: limit reach. That is the Rule of Two we just covered.  Two: separate planning from untrusted data. The agent commits to its plan, meaning which tools it will call, before it reads anything untrusted. Retrieved text can fill in details but cannot add new steps. That still leaves a gap: an attacker's text could supply a dangerous detail, such as their own address as the email recipient. Research systems like CaMeL close that gap by tracking where each piece of data is allowed to flow.  Three: mediate every action. The model never acts directly; it asks. Plain, deterministic code checks each request against a schema, against business rules such as "no discount over 30 percent", and against the requesting user's own permissions, never a broadly privileged service account.  The second group reduces the odds and tells you when something leaked.  Four: mark and filter. Wrap outside content in delimiters so the model knows it is data, and scan it with tools such as Amazon Bedrock Guardrails' prompt-attack filter. These noticeably cut success rates, but they are probabilistic. Never rely on them as your only defense.  Five: keep secrets out. Assume your system prompt will be extracted eventually, so credentials and access logic don't belong there. A canary token is a unique marker hidden in the prompt; if it ever appears in an output, you know the prompt leaked. It is an alarm, not a lock.  Quick check for the room: our retail offer generator reads customer reviews, which is untrusted input, and uses purchase history, which is sensitive data. Which corner must we remove, and what does that mean for how offers get delivered?  Answer: remove "change state or communicate out". The generator only proposes an offer; a separate, deterministic service validates it against business rules and delivers it.  So far we have protected the system from what it reads. - Extraction and Inference Attacks

- band = "high"

- band = "medium"
- else:
- band = "low"

> Notes: Why does returning a raw probability from your churn endpoint help an attacker, and what does returning only a label actually buy you?  Two different attacks share the name extraction. Model extraction copies functionality: query the API, train a substitute on the answers; Tramèr and colleagues produced near-equivalent copies of models on commercial machine-learning-as-a-service platforms. Training data extraction recovers memorized records;   Carlini and colleagues pulled hundreds of verbatim sequences, including names, phone numbers, and emails, from GPT-2. Different attacks, different controls: quotas and anomaly detection for the first; scrubbing, differential privacy, and output filters for the second. *Differential privacy does nothing to stop someone copying your model's behavior, and watermarking is not yet a dependable control.  Differential privacy is a mathematical guarantee that the result of an analysis, or a trained model, barely changes whether or not any one person’s data is included. If adding or removing your record can’t noticeably change the output, then the output can’t reveal much about you.  Membership inference asks whether a specific person's record was in training. For health or financial data, that answer alone is a privacy violation. Detailed confidence scores help because each one is precise feedback on how close a guess is. Correct anything they read earlier: it is not "gradient information." And returning only labels raises the cost without removing the risk, because label-only attacks also work. > Notes: How can an attacker compromise an AI system without ever touching our code or our prompts?  This slide covers three attacks that come in through the side doors: the data the model learns from, the inputs it receives, and the components we download and trust. Let's take them left to right.  Data poisoning corrupts the teacher. An attacker slips malicious examples into the training data so the model learns a hidden behavior, typically a backdoor: the model acts normally until it sees a specific trigger, then does what the attacker wants. The headline number is from a 2025 study by the UK AI Security Institute, Anthropic and the Alan Turing Institute. About 250 poisoned documents were enough to implant a backdoor in models ranging from 600 million to 13 billion parameters. The point is that the number did not grow with model size. Bigger models train on far more clean data, but the attacker still only needs a few hundred documents. And separate research shows these backdoors can survive the safety training we rely on to clean models up.  Poisoning is not only a training problem. In a RAG system, the retrieval corpus is effectively a training set the model consults at answer time. The PoisonedRAG study showed that inserting a handful of crafted documents can steer the answers to targeted questions. If your corpus ingests customer reviews or web pages, anyone can contribute to it. The controls: track where every record came from, run quality gates before training, and keep trusted sources separate from user-submitted content.  The middle column is adversarial inputs, and the key difference is timing. Poisoning corrupts the teacher during training. Adversarial inputs fool the student at test time, and the model itself is unchanged. A model does not understand concepts the way we do; it learns statistical patterns, and those patterns have blind spots. A tiny, deliberate change can push an input across the model's decision line. Think of an optical illusion designed for one particular model.  Look at the example on the slide. The two words look identical to you. But the second one starts with a Cyrillic letter, not a Latin i. A filter that blocks the first word sees the second as a word it has never encountered, and lets it through. In vision, the classic demonstration is an image with carefully computed noise, invisible to us, that makes a classifier confidently call a panda a gibbon.  The stakes are highest where adversaries have a motive to probe and the model's decision triggers action automatically: fraud detection, content moderation, credit scoring. The controls each do something different. Normalizing encodings removes the trick itself, by stripping invisible characters and mapping look-alike letters to standard ones. Routing low-confidence predictions to people is a backstop, though the best adversarial examples fool the model confidently. Adversarial training is a vaccine: include attack examples in training so the model learns to resist them.  The right column is the supply chain. Nobody builds an AI system from scratch. We download libraries, pretrained models, datasets and tools, and every one of them is a supplier we trust. A supply chain attack compromises the supplier, and the compromise flows into our system. It is like a contaminated ingredient: a clean restaurant kitchen does not help.  The AI-specific surprise is in the code block: a model file can run code. Many PyTorch checkpoints are saved with Python's pickle format, which stores instructions for rebuilding objects, and those instructions can include "run this command". Newer PyTorch versions block this by default, but older versions, or code that turns the safeguard off with weights_only equals False, will execute whatever the file contains. The safer path is the safetensors format, which stores only numbers, so there is nothing to execute. And if you must use a pickle, scan it first with a tool like ModelScan.  Scanning has a limit, which is the first bullet. A backdoored model contains no malicious code, just learned behavior, so no scanner will find it. Your defense is knowing who published the model, and testing it.  That leads to checksums versus signatures. A checksum proves the file matches what the website posted. But if an attacker controls the website or the publisher's account, they post a matching checksum for their tampered file. A signature proves who published the file, tied to an accountable identity. Neither proves the model is safe; a signature tells you whom you are trusting.  Tools and MCP servers are suppliers too. Their code runs with your agent's permissions, and their descriptions are text the model reads, which makes them a channel for prompt injection.  Finally, keep an AI bill of materials: an ingredient list of every model, dataset, library and tool in each system. When a supplier turns out to be compromised, you can answer "which of our systems use this?" in minutes instead of days.  A real example to remember: in December 2022, PyTorch's nightly builds pulled a malicious package called torchtriton from the public Python package index instead of PyTorch's own repository. For several days, Linux users installing those builds ran code that stole data from their machines. No model was involved; the trusted install process delivered the attack.  Quick question for the room: your team downloads a popular open model from a public hub, it passes ModelScan, and its checksum matches. What risk is still left?  Answer: a backdoor trained into the weights. Scanning finds code, and checksums prove the file is unchanged, but neither tells you whether the model's behavior is trustworthy. That depends on the publisher and on your own testing.  So far we have looked at attacks on what the model learns, receives and depends on. Next, we look at what happens when we give a model the power to act, and why excessive agency turns every one of these threats into a real incident.
