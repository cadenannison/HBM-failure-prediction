> Notes: QUESTION: Why would you deliberately make an auto-scaler slower at removing capacity than at adding it?  Walk the code top to bottom. register_scalable_target tells Application Auto Scaling which variant it may manage and the bounds. MinCapacity of 1 is a latency decision, not a cost decision: with no warm instance, the next request waits for one to be provisioned, and that takes minutes. MaxCapacity of 2 isn't a design choice. It's your account's endpoint quota. In Lab 5 you'll request two ml.m5.large instances, so two is your ceiling whatever the policy says.  put_scaling_policy uses target tracking on invocations per instance, targeting 1,000 per minute. Those are the Lab 5 values. Now the cooldowns: 60 seconds out, 600 seconds in. If both were short, a spike adds an instance, traffic dips for a moment, the instance is removed, the spike returns, and you've built an oscillator that pays for instances it never uses and hurts latency on every cycle.  Look at the chart. Demand jumps at minute 4. By default the scale-out alarm needs three consecutive one-minute data points, and then the new instance has to be provisioned, so capacity doesn't arrive until around minute 13. For nine minutes the single instance carries 1,800 a minute. On the way down, the scale-in alarm waits for about fifteen minutes of low traffic, so the second instance stays until around minute 38. Fast out, slow in, by design.  The lesson for an architect: auto-scaling handles gradual change. It does not absorb a spike that arrives in seconds. If you know a spike is coming, a product launch or Black Friday, raise MinCapacity on a schedule ahead of time.  TRANSITION: Auto-scaling is for traffic you can't predict. When the work is fully known in advance, there's a better tool.

- Warm Floor vs. Cold Start
- A warm floor pays for idle hours. A cold start pays in failed requests while the first instance boots.

> Notes: Warm floor (MinCapacity=1): at least one instance is always running, so the first request after a quiet period is answered at normal latency. You pay for that instance every hour, including nights and weekends.  Cold start (MinCapacity=0): only possible when the endpoint hosts inference components, and the endpoint config's ManagedInstanceScaling must also set MinInstanceCount=0. Target tracking scales the copy count in to zero when idle. Scaling back out is a separate step-scaling policy, triggered by a CloudWatch alarm on NoCapacityInvocationFailures — SageMaker emits that metric when a request arrives and no copy can serve it. AWS notes provisioning takes several minutes, and invocations fail until it finishes.  Chart: requests start at minute 5. The warm floor serves them immediately. The cold-start endpoint has no capacity until about minute 12, so minutes 5–12 are failed requests. After traffic stops at minute 28, target tracking takes roughly 15 minutes to scale back in to zero. Timings are illustrative.  Rule of thumb: warm floor for anything with a latency SLA or user-facing traffic (Northstar churn-prod). Cold start for dev/staging, internal tools, and bursty or scheduled workloads where clients can retry. If callers can't tolerate errors but you still want zero idle cost, consider asynchronous inference (requests queue instead of failing) or serverless inference.

- batch_score.py
- from datetime import date
- from sagemaker.transformer import Transformer
- t = Transformer(model_name="northstar-churn-v3-0",
- instance_count=10, instance_type="ml.m5.xlarge",
- output_path="s3://northstar-artifacts/scores/",
- strategy="MultiRecord", max_payload=6,   # MB
- max_concurrent_transforms=4,   # = vCPUs/instance
- accept="text/csv", assemble_with="Line")  # 1 row/line
- # input prefix holds >= 10 CSV parts: one per instance
- t.transform(data="s3://northstar-processed/scoring/",
- content_type="text/csv", split_type="Line",
- job_name=f"northstar-churn-batch-{date.today():%Y-%m-%d}")
- 45 min
- vs. 6+ h on one instance
- $1.73
- per run (~$1.38 serially)
- At ~$0.23 per instance-hour; prices vary by region

> Notes: This slide shows a production-scale run: 10 × ml.m5.xlarge. Lab 5 uses a smaller configuration, so students need transform quota for ml.m5.large, not for the instance type shown here.  Batch Transform distributes whole S3 objects across instances; it does not split one file across machines. The scoring prefix therefore needs at least as many CSV parts as instances (10+ here), or most of the fleet sits idle while still being billed. split_type="Line" only splits records within each file.  split_type="Line" tells Batch Transform how to cut each input file into individual records: every newline marks the end of a record, so each CSV row is one record.  MultiRecord packs many rows into each request (up to max_payload MB). max_concurrent_transforms=4 matches the 4 vCPUs of an ml.m5.xlarge. accept and assemble_with="Line" make the output one score per line; without assemble_with, mini-batch outputs are concatenated with no separator, and rows can run together.  The job name is built from today's date because transform job names must be unique; a hardcoded name fails on the second night.  Cost: 10 instances × 0.75 h ≈ 7.5 instance-hours vs. ~6 on one instance. Parallelism buys wall-clock time, not cheaper compute.

> Notes: QUESTION: When AWS runs the model servers, what is left for you to tune?  You don't control Bedrock's infrastructure, scaling or cold starts. You control five things.  Model tier. The labs use Claude Haiku 4.5 through the us. inference profile, the ID at the top of the code. Larger tiers are better at hard reasoning and slower.  Prompt length and output length. Every input token costs time, and output length drives latency most. maxTokens is a ceiling, not a speed setting. Constrain the format in the prompt, then set the cap to match; it also stops runaway responses and bounds cost.  Streaming. For anything a person watches, converse_stream shows tokens as they arrive. The cachePoint after the static system prompt lets Bedrock reuse that prefix for five minutes after the last hit, and cache reads bill at a reduced rate. NorthStar's offer prompt is about 800 tokens, so on Haiku 4.5 it never caches, and the call succeeds without a word of warning. - Regulated DR
- Finance and health often mandate a separate DR site.
- Not replicated: live request state and active agent sessions. Sessions restart; that is acceptable here.

- Endpoints · Bedrock KB · Feature Store · prompts
