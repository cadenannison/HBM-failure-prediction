A row coming out of this stage is still a transaction.” Processed zone — 157,627 rows “That gives us 157,627 clean transactions in processed/customers/, stored as Parquet. Now we deliberately change the grain. We collapse exactly once, by aggregation.  Instead of asking, ‘What happened in this transaction?’ we’re now asking, ‘What do we know about this customer?’ Multiple transaction records therefore become one customer feature vector.” Feature zone — 9,999 customers “That aggregation produces exactly 9,999 customer feature vectors. Those vectors go into features/customers/, and ultimately into the Feature Store. This is the representation our downstream machine-learning workflow needs.” Call out the common mistake “The most common mistake in this lab is collapsing too early. If your processed dataset contains 9,999 rows instead of 157,627, you’ve turned the transaction dataset into a customer dataset during cleaning. You may still have valid-looking data. Your code may run perfectly. But you’ve destroyed information that later tasks need. ## Slide 8
- Data Pipeline
- Ingest raw data at rest — customer transaction records and behavioral events land in raw/ as CSV files
- Discover schema automatically — a Glue Crawler scans raw/ and registers the schema in the Glue Data Catalog so ETL jobs can query it without hardcoded column definitions
- Transform and validate — a Glue ETL job reads from the catalog, applies type enforcement and null handling, and writes Parquet to processed/
- Engineer features and label them — a second Glue ETL job reads processed/, splits it into an observation window and a holdout window, computes 13 churn-predictive features from the observation window, derives churn_label from the holdout, and writes to features/
- Register features for ML — a SageMaker Feature Group ingests the feature vectors so training jobs in Labs 3–4 can pull them without re-computing
- Enforce data boundaries — DataEngineer writes raw/, processed/, and features/ but cannot write artifacts/; MLEngineer reads features/ and writes artifacts/; ModelMonitor reads artifacts/ and writes CloudWatch metrics only
- Expire stale data automatically — raw files older than 90 days are deleted by S3 lifecycle rules

The DataEngineer needs read access to artifacts/glue/ because Glue has to retrieve the script it is going to execute. But it cannot start a processing job. In a later lab, another role will be responsible for taking action.” Move to the access matrix “The matrix on the upper right is the same architecture expressed as permissions. ## Slide 18
> Notes: Presentation Notes — Principle 2, Continued: The Five Permissions Nobody Guesses Speaker notes: This slide highlights one of the most frustrating parts of working with AWS: the permission that is actually missing is often not the permission named in the error message. The key idea is to learn to translate the error from an API symptom into the underlying IAM requirement. First: SageMaker needs sagemaker.amazonaws.com in the role's trust policy. If that is missing, AWS may report that the execution-role ARN is invalid. The ARN itself can be perfectly correct—the problem is that SageMaker cannot assume the role. Second: Feature Store checks the S3 bucket ACL, so s3:GetBucketAcl is required. Without it, an otherwise valid S3 URI can produce an "Invalid S3Uri" error. Third: glue:GetConnection is needed because Glue resolves the VPC connection before the actual ETL script runs. A Data Catalog connection error can therefore be an IAM problem rather than a configuration problem. Fourth: Glue creates and tags network interfaces when it runs inside a VPC. That means the role needs ec2:CreateTags on the network interfaces it creates. Fifth: Feature Store's offline store writes objects with ACLs, so s3:PutObjectAcl is required for those feature writes. The practical lesson: don't simply copy the wording of an AWS error into your troubleshooting process. Ask, "What API is failing, what operation is AWS trying to perform at this point, and what permission would allow that operation?" For Lab 2, this is especially important because many of these failures happen before student code executes. If a Glue job fails during VPC setup or Feature Store fails while validating S3, changing the Python script won't fix the problem. Rule of thumb: AWS error messages usually describe the symptom at the API boundary, not the missing permission. IAM troubleshooting is therefore an iterative process: read the error, identify the underlying API operation, add the narrowly required permission, and rerun. ## Slide 19
> Notes: Presentation Notes — Principle 3: The Data Plane Gets No Public IP Speaker notes: This slide captures the network architecture change between Lab 1 and Lab 2. The central principle is simple: customer data should stay on a private data plane.  Start with the Lab 1 pattern On the left, Lab 1 puts Studio directly in a public subnet. That makes the architecture easy to understand and easy to reach: Studio can route directly through the Internet Gateway. But that simplicity comes with the wrong security boundary for customer data. The compute environment itself is sitting in a subnet designed for direct Internet connectivity. The important point isn't that public subnets are inherently bad. It's that the data-processing components should not require public IP connectivity.  Now look at the Lab 2 pattern On the right, Lab 2 separates the public and private responsibilities. The public subnet contains the NAT Gateway and its EIP. The NAT needs to be public because it ultimately sends outbound traffic through the Internet Gateway. The private subnet, 10.0.1.0/24, contains the SageMaker Domain and Glue workers. These resources don't have direct Internet ingress. When a private resource needs outbound Internet access, the path is:  Private subnet → NAT Gateway → Internet Gateway → Internet The critical distinction is that this is outbound-only from the perspective of the private data plane. The red dashed arrow shows that an unsolicited inbound connection from the Internet cannot simply enter the private subnet. The route table matters The private route table has the local VPC route and then: 0.0.0.0/0 → nat-xxxx That default route tells private resources where to send traffic destined outside the VPC. The NAT itself lives in the public subnet because it needs a route to the Internet Gateway. A useful mental model is: Public subnet: infrastructure that provides Internet connectivity.Private subnet: infrastructure that processes the data. VpcOnly is only half the fix The lower-left panel highlights an easy mistake. Simply moving the Studio Domain into a private subnet isn't enough. If SageMaker's app_network_access_type isn't changed to VpcOnly, Studio can still use a SageMaker-managed network path rather than being forced through the VPC routing you've designed. So the two changes belong together: Private subnet + VpcOnly = traffic follows your VPC routing. This is an important Lab 2 lesson because networking isn't just about where an AWS resource is placed. It's also about which network path the service is allowed to use. Glue has another VPC-specific requirement The middle panel focuses on Glue. When Glue runs inside the VPC, it requires a NETWORK connection and a security group configuration that allows the Glue workers to communicate appropriately. The unusual detail is the security group rule: Glue expects a self-referencing all-ports rule, meaning self = true. Contract tests ask: Did an upstream change violate something a downstream consumer depends upon? We might test: required fields, datatypes, semantic constraints, allowed values, quality thresholds, schema compatibility. If the producer removes customer_id or changes amount from dollars to cents, we want to detect that before the change reaches production.” A useful connection is: The data contract defines the promise; the contract test verifies compatibility with that promise.  4. Volume Tests — does it still work at production scale? “At the top are volume tests.  A pipeline that works perfectly with 1,000 records may behave very differently with 500 million. Here we’re testing things such as: processing time, scalability, memory usage, partitioning behavior, and bottlenecks. These tests are expensive, so we run relatively few of them and less frequently—perhaps before a major release or significant architecture change.”  Why the pyramid shape matters “The width of the pyramid represents where most of our testing effort should occur. At the bottom: Many tests → fast → cheap → narrow scope As we move upward: Fewer tests → slower → expensive → broader scope The goal is to detect problems at the lowest and cheapest possible level.” For example: “If a feature calculation is wrong, I’d much rather discover it in a five-second unit test than after running a 45-minute Glue job over millions of records.”  Connect this to CI/CD “This testing pyramid becomes particularly powerful when integrated into CI/CD. A proposed pipeline change might move through: Code commit→ Unit tests→ Integration tests→ Contract tests→ Deploy→ Production monitoring  If a test fails, we stop the change before bad data propagates downstream.” Testing and observability are complementary “One distinction is important. Testing asks: Does the system behave correctly under conditions we’ve anticipated? Observability asks: What is the system actually doing in production? We need both. Tests prevent known classes of problems. Monitoring and observability help us discover behaviors we didn’t anticipate.” Connect to AI “Why does this matter for machine learning? Because a data pipeline can run successfully while silently producing incorrect features. And once incorrect features reach the model, the model may still return perfectly valid-looking predictions. So the dependency chain is: Pipeline correctness → feature correctness → model reliability. Testing the data system is therefore part of testing the AI system.” Closing takeaway “The key principle is: Catch failures as early, cheaply, and locally as possible. Use unit tests for transformation logic, integration tests for component interactions, contract tests for producer-consumer compatibility, and volume tests for production-scale behavior. The result is the message at the bottom of the slide: Higher confidence → more reliable data → better AI.”    AI Data Pipeline Testing Hierarchy:  Unit Tests (per transformation function): Input: known DataFrame with controlled values Expected output: explicitly specified Examples: test that recency_days returns 0 when transaction_date == today, NaN when no transactions  Integration Tests (per pipeline): Run the complete Glue job on a 1,000-row sample Validate output schema, row count, and quality metrics Must complete in < 5 minutes (fast feedback loop)  Data Contract Tests (at pipeline boundary): Validate that pipeline output conforms to the signed data contract Run automatically on every pipeline execution Contract violations halt the pipeline  Volume/Performance Tests (monthly or pre-release): Run the pipeline on the full dataset (4.5M transaction records) Validate that it completes within the SLA window  Notes: "Data pipeline testing is the most commonly skipped engineering practice in AI projects. Teams test their model code (sometimes) but not their data transformation code (rarely). A bug in a feature computation function that passes all unit tests but fails on the actual production data distribution is exactly the kind of failure that causes production incidents."
