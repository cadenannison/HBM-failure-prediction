> Notes: Opening. Before you choose a technique, ask one question: what kind of problem is this? The answer sends you down one of two branches, and most of the wasted effort in AI projects comes from picking the wrong branch. Left branch: traditional ML. If your input is structured rows and columns and you need a number or a label, use traditional machine learning. Fraud scores, churn risk, and demand forecasts all live here. This is what you build in the Northstar labs with XGBoost. You train every weight yourself, but the model is small, so it takes hours and costs very little. For this kind of problem it usually beats a language model on accuracy, cost, speed, and explainability. Right branch: foundation models. If the input is unstructured (text, images, documents) or you need generated language, you start from a foundation model. The question then becomes how much you need to change it. Read the four columns left to right as increasing effort. Prompt engineering. Always start here. You change only the instructions. You need a few examples, you get a result in hours, and it costs almost nothing to try. Many projects never need to go further. RAG. Move here when the model lacks your data or needs current facts. You don't change the model. You hand it the relevant documents at run time. Think of it as an open-book exam. Fine-tuning. Move here when prompts can't produce a consistent style or format. Now you are changing some of the model's weights, and you need hundreds to thousands of labeled examples. Think of it as studying before the exam. Sometimes combined. RAG and fine-tuning solve different problems, so they are not steps on a ladder. RAG supplies facts, and fine-tuning shapes behavior. Some teams use both: RAG fetches the current policy, and a fine-tuned model answers in the company's voice. Most teams need only one, and many need neither. Train your own model. This is rarely needed. You would do it only when no existing model fits your data, for example a new data type or a highly specialized domain. Look at the cost row: the jump from three dollar signs to five understates it. This step costs orders of magnitude more and takes months. Compare the two ends. Look at the "What changes" row. Traditional ML and "Train your own model" both train all the weights. Now look at time and cost: one is hours and a dollar sign, and the other is months and five. The difference is model size and data volume. That is why traditional ML sits on its own branch and not on the spectrum. The rule. On the right branch, start at the left and move right only when you can name the specific failure that forces you to. The "Use when" row gives you that failure for each step. Not on the slide. Two things to mention aloud. Running cost. The slide shows the cost to build. RAG adds retrieval infrastructure and longer prompts on every request, and a fine-tuned or custom model has to be hosted. The branches work together. An agent can call your XGBoost fraud model as a tool and then explain the score in plain language. Discussion prompt: "Northstar wants to predict which customers will return a product, and also to draft a personalized email to each one. Which branch?" Answer: both. Return prediction is rows in and a label out, so it is traditional ML. Drafting the email is generated language, so it is a foundation model, and prompt engineering is probably enough. Follow-up: "What would push the email task to RAG?" Answer: needing each customer's order history or the current return policy in the message.

- Model selection
> Notes: OpeningBefore we tune a single hyperparameter, we need to choose what kind of model to build. The most reliable first question isn't about algorithms at all. It's what type of data do we have? The shape of the data narrows the choice more than anything else.  Three branchesThe tree splits three ways: Tabular: rows and columns, like customer records, transactions, and usage logs. Most business data looks like this. Text and documents: PDFs, emails, chat logs, knowledge bases. Images: photos, scanned diagrams, video frames. Then we ask a second question: what's the goal? Predicting a label, generating an answer, and detecting an object lead to different tools, even on the same data.  The NorthStar path (highlighted)Our case is the gold path on the left. We have tabular customer data, and we want to predict whether each customer will churn, which is a yes/no classification problem. For that, gradient-boosted trees are the default starting point, and there's good evidence for it. On tabular data of this size, boosted trees routinely match or beat deep learning, train in minutes on a CPU, and handle missing values and mixed feature types without much preprocessing.  Look at the three leaves as a ladder rather than rivals: Start with a simple baseline, such as logistic regression or a single decision tree. It's quick, easy to explain, and it tells you whether the harder models are actually earning their complexity. XGBoost is our main model: strong accuracy, fast, and mature tooling on SageMaker. LightGBM is the same family of algorithm, usually faster on very large datasets. It's a reasonable alternative, not a different kind of model. One honest caveat about "interpretable": a 500-tree ensemble isn't interpretable by inspection. We make it explainable with tools like SHAP, which is exactly what we did a few slides ago.  Text branchFor text, the three options aren't alternatives to each other; they stack. Foundation model: you usually start with a general-purpose LLM, prompted well. RAG: if it needs your facts, like policies, product docs or support history, you add retrieval, so the model answers from your documents instead of from memory. Fine-tuning: you reach for this last, when you need a consistent style, format or specialized behavior that prompting and retrieval can't deliver. Rule of thumb: try the cheapest step first and move up only when it fails.  Image branch CNN (or a small vision model you train yourself): best for a narrow, well-defined task with plenty of labeled examples, such as spotting defects on one product line. Vision foundation model: best when labels are scarce or the task is broad. It can classify or describe images with few or no training examples.  ClosingThe takeaway isn't "always use XGBoost." The problem chooses the model. Identify the data type, name the goal, start with the simplest thing that could work, and let evidence (the MLflow comparisons we saw) justify anything more complex.  TransitionWe've chosen gradient boosting for NorthStar. Next, let's look at how we train and track it. ## Slide 8
- Why XGBoost (or equivalent)?
- The goal of model development isn’t to use the most sophisticated model.
- It’s to use the appropriate level of sophistication for the problem we’re trying to solve.
> Notes: Presentation Notes — Why XGBoost and Not an LLM?  Opening: Start with the problem, not the technology This slide reinforces an important principle in model development:  The best model depends on the structure of the problem—not on which technology is currently getting the most attention. In this example, we’re trying to predict customer churn over the next 90 days.  We have about 250,000 historical customer records, approximately 18 months of data, and a churn rate of roughly 12%. For each customer, we’ve engineered eight structured features. This is a classic supervised binary-classification problem.  The question is: should we solve it with a large neural model—or perhaps an LLM—or with something specifically designed for structured tabular data, such as XGBoost? For this problem, XGBoost is a very natural candidate.  First: Why isn’t this really an LLM problem? Before comparing XGBoost with a neural network, notice what our inputs actually look like. We’re not analyzing language. We’re not asking the model to understand an email, summarize a customer conversation, or interpret a support ticket. Our desired output is essentially: 	Probability of churn within 90 days = 0.73 That’s an important clue.  An LLM is optimized around sequences of tokens and language-like representations. Here we already have a relatively small number of meaningful, structured variables. We don’t need a model to discover linguistic meaning. We need a model to learn a function approximately like: eight customer features → probability of churn. Factor 1 — Data Type XGBoost is particularly well suited to structured tabular data. Decision-tree ensembles can naturally discover nonlinear relationships and interactions among variables. For example, perhaps a reduction in product usage isn’t particularly concerning by itself. And perhaps two support calls aren’t particularly concerning either. But: usage declining + multiple support cases + month-to-month contract might be strongly associated with churn. Tree-based models are very good at discovering these kinds of conditional interactions. A neural network can also learn them, but that doesn’t mean it is automatically the better tool. Factor 2 — Training Data Size Our dataset contains about 250,000 examples. That’s substantial by ordinary business analytics standards, but it isn’t necessarily the scale at which a larger neural architecture has a compelling advantage for a small tabular feature set. XGBoost can perform extremely well with datasets in this range. Factor 3 — Interpretability Interpretability can be particularly important in a churn application. Suppose the model tells us that a customer’s churn probability is 78%.  The business is likely to ask: Why? With a tree-based model, we can use feature importance and, more usefully, techniques such as SHAP values to investigate which features contributed to an individual prediction. We might discover: Churn probability: 78%  Major contributors: product usage declined substantially, three recent support incidents, month-to-month contract, recent payment failure. That is much more actionable than simply telling a retention team, “The model says this customer is high risk.” And this distinction matters operationally: prediction tells us who may churn; explanation can help determine what intervention might make sense. Factor 4 — Training Time XGBoost models on a dataset like this can often train quickly. That matters because model development is iterative. We’re not going to train the model once and declare victory. We may test different features, different time windows, class weighting, sampling strategies, hyperparameters, and validation schemes. Fast training means we can run more experiments. So training efficiency isn’t simply about saving compute cost. It affects the speed of the entire experimentation cycle. Factor 5 — Hyperparameter Tuning XGBoost certainly has hyperparameters—tree depth, learning rate, number of estimators, subsampling, regularization, and others. But the modeling behavior is well understood, and mature tools exist for tuning these parameters. With a more complicated neural architecture, we may introduce additional decisions about architecture, layer widths, activation functions, optimization, learning-rate schedules, regularization, batch sizes, and training behavior. Again, additional complexity is worthwhile when it produces sufficient benefit. But complexity should have to earn its way into the architecture. Factor 6 — Production Serving Finally, consider deployment. This model doesn’t need to respond conversationally in 200 milliseconds. The slide says we’re doing nightly batch scoring. Perhaps every night we score all active customers and write something like: customer_id → churn_probability into a database. The next morning, the CRM system identifies customers above some intervention threshold and provides them to the retention team. That is an extremely simple production architecture. An XGBoost model can be small, inexpensive to execute, and easy to deploy. We don’t need GPUs or an LLM inference service simply to calculate one probability from eight features. The subtle point: XGBoost and an LLM could both belong in the solution I would emphasize this distinction because it connects directly to the previous enterprise-support example. Suppose we also have customer emails, call transcripts, support tickets, and account-manager notes.  Now an LLM may become extremely valuable. For example, the LLM could analyze thousands of support interactions and extract: Customer sentiment: negativeCancellation intent: highPrimary complaint: repeated service outagesCompetitor mentioned: yes  Those extracted variables could then become additional features for the XGBoost churn model.  So the architecture might become: Unstructured customer interactions → LLM → structured features → XGBoost → churn probability That is often a better way to think about enterprise AI than asking: “Should I use XGBoost or an LLM?”  The better question is: “Which model is best suited to each part of the problem?” Important teaching qualification Our hypothesis is: Given 250,000 observations, eight engineered tabular features, a binary classification target, and a nightly batch workload, XGBoost is a strong baseline with several practical advantages. Then we test that hypothesis. If a neural network—or another model such as LightGBM, CatBoost, logistic regression, Random Forest, or a tabular neural architecture—produces materially better validated performance, we consider it. Model selection is ultimately an empirical question. Transition to model development This gives us a useful workflow for the rest of the lecture. We don’t start by saying: “I want to build an XGBoost model.” And we certainly don’t start by saying: “I want to use an LLM.”  We start with: What is the target? Churn within 90 days. What does the input look like? Eight engineered tabular features. How much training data do we have? 250,000 historical observations. What are our operational requirements? Nightly batch predictions. What does the business need from the model? Accurate probabilities that can be understood and operationalized.  Only then do we choose candidate algorithms, train them, evaluate them on unseen data, and determine which approach actually performs best.  The goal of model development isn’t to use the most sophisticated model. It’s to use the appropriate level of sophistication for the problem we’re trying to solve.

## Slide 9
- Training the Churn Model: Key Engineering Decisions
> Notes: Brief Presentation Notes — Training the Churn Model: Key Engineering Decisions This slide emphasizes that choosing XGBoost is only the beginning. Model quality depends heavily on the engineering decisions surrounding training, evaluation, and deployment.  1. Data splitting — simulate production. A simple random split can produce misleading results when observations are time-dependent or when the same customer appears multiple times. For churn, we generally want the validation and test data to resemble the future data the model will encounter. A time-based split—or an appropriate grouped split—helps prevent leakage and gives us a more realistic estimate of production performance.  2. Feature engineering — more isn’t necessarily better. We don’t automatically give the model every available variable. Features should be relevant, available at prediction time, and free from information that reveals the future. We also need consistent handling of missing values and transformations. Domain knowledge is especially valuable here: good features often capture meaningful behaviors such as declining usage, changes in purchasing patterns, or increasing support activity.  3. Model tuning — defaults are a baseline, not necessarily the final model. XGBoost has important hyperparameters controlling tree depth, learning rate, regularization, and the number of trees. We systematically explore those choices using techniques such as random search or Bayesian optimization, evaluating each candidate against validation data rather than the training set.  4. Deployment — reproducibility continues into production. A model isn’t finished when training completes. We need a repeatable process for packaging, versioning, testing, deploying, and monitoring it. CI/CD and MLOps practices reduce manual errors and allow us to trace a production prediction back to a particular model version.  The overall takeaway is: Production model quality is determined by the entire ML engineering process—not simply by the algorithm. A sophisticated algorithm combined with data leakage, poor features, inappropriate validation, or an unreliable deployment process can produce a worse production system than a simpler model supported by sound engineering. ## Slide 10
- Evaluating the Churn Model: The Lab 3 Gate
> Notes: Brief Presentation Notes — Evaluating the Churn Model: The Lab 3 Gate This slide highlights two different questions we need to answer before accepting our churn model: Can it distinguish churners from non-churners, and can we trust the probabilities it produces?  1. ROC Curve — How well does the model discriminate? The ROC curve evaluates the trade-off between identifying true churners and incorrectly flagging customers who will not churn. An AUC of 0.76 indicates useful discrimination—the model is substantially better than random, although there is still room for improvement. The marked 0.4 threshold illustrates an important point: the model produces probabilities, but the business ultimately has to decide where to act. Lowering the threshold identifies more potential churners but also generates more false positives. The appropriate threshold therefore depends on the cost of a retention intervention versus the cost of missing a customer who churns.  2. Calibration Plot — Can we trust the probability? Discrimination isn’t enough. If the model assigns a customer a 70% probability of churn, we’d like approximately 70% of customers receiving predictions around 0.70 to actually churn. The closer the calibration curve is to the diagonal, the more closely predicted probabilities correspond to observed outcomes. This matters because churn probabilities may drive business decisions. A well-calibrated 0.80 probability should represent substantially greater business risk than 0.30, not merely a higher model score.  What a calibration plot is A calibration plot answers one question: when the model says 30%, do about 30% of those customers actually churn? AUC measures ranking: whether churners get higher scores than non-churners. It says nothing about whether the scores mean what they say. A model can rank perfectly and still predict 0.9 for customers who churn only 40% of the time. Calibration checks the second property. That matters for churn whenever you use the probability as a number rather than just a ranking. For example, expected loss = P(churn) × customer value, used to decide who gets a retention offer. If you only need "call the top 500 riskiest customers," ranking (AUC) is enough. How it's made Score a held-out set. Use the validation or test set, never the training data, and take predicted probabilities (predict_proba), not 0/1 labels. Bin the predictions, for example into 10 bins: 0–0.1, 0.1–0.2, and so on. Equal-count ("quantile") bins work better when most predictions are low, which is typical for churn. For each bin, compute two numbers:  x = the average predicted probability of the customers in it y = the fraction who actually churned Plot the points against the diagonal. Points below the diagonal mean the model overpredicts risk; points above mean it underpredicts.  python from sklearn.calibration import CalibrationDisplay CalibrationDisplay.from_predictions(y_test, p_test, n_bins=10, strategy="quantile")  Good practice is to add a histogram of how many customers fall in each bin, plus a summary number such as the Brier score or expected calibration error.  Data needed A true churn label for each customer, defined over a fixed window. For example: scored on March 1, did they churn by May 31? Churn is only known after the window closes, so the evaluation set has to come from a period old enough to have outcomes. The model's predicted probability for each of those customers. Enough churners in every bin. High-probability bins often hold only a few dozen customers, so their points are noisy.   The key distinction is:  ROC/AUC asks: “Can the model rank risky customers correctly?”Calibration asks: “Do the predicted probabilities mean what they say?”   For the Lab 3 gate, we therefore shouldn’t approve the model based on a single accuracy number. We want evidence that it provides both useful discrimination and meaningful probabilities before moving toward production.   The Stage 6 Gate Criteria for NorthStar Churn Model:  Primary Metrics: AUC (Area Under ROC Curve) ≥ 0.72 — measures overall discrimination ability Precision@threshold=0.4 ≥ 0.65 — of customers flagged as at-risk, 65% must actually churn Recall@threshold=0.4 ≥ 0.55 — must catch at least 55% of actual churners  Secondary Metrics: Feature importance: recency_days must be in top-3 features (sanity check) Calibration: predicted probabilities should match actual churn rates (use reliability diagram)  Business-informed threshold selection: The 0.4 threshold is chosen by the business: it controls the volume of retention offers sent Lower threshold = more offers = more cost = more churners caught Higher threshold = fewer offers = less cost = fewer churners caught Threshold is a business decision, not a model decision  Notes: "The gate criteria were set before the model was trained — in the Stage 1 Project Charter. ## Slide 11
- Reproducibility checklist
> Notes: Brief Presentation Notes — Reproducibility Checklist  This slide asks a fundamental question: If we run this experiment again tomorrow—or six months from now—can we reproduce the result? Reproducibility requires controlling more than just the model code.  1. Fix random seeds. Many ML operations involve randomness—data sampling, initialization, and optimization. Controlling seeds reduces unintended variation between runs, although some hardware and ML operations can still introduce nondeterminism.  2. Version the data and dependencies. Knowing which code produced a model isn’t enough. We also need the exact training data and software versions. If either changes, we may get a different model.  3. Make the training environment immutable. Changes to Python packages, operating systems, CUDA versions, or other dependencies can alter results. A defined environment helps ensure that we’re actually rerunning the same experiment.  4. Make preprocessing deterministic. This is the failed item in our example. If preprocessing randomly samples, partitions, or transforms data without controlling that behavior, identical training code can receive different inputs. Our reproducibility score is therefore 5 out of 6.  5. Log the complete experiment. We should capture parameters, metrics, code or configuration versions, data references, and model artifacts. Tools such as MLflow give us the provenance needed to reconstruct and compare experiments.  6. Containerize training. Containers package the training code and its dependencies into a consistent runtime environment. This is one reason containerized training in SageMaker is valuable: the environment itself becomes part of the reproducible training specification.  The main takeaway is: Reproducibility means tracing a model back to the exact data, code, configuration, environment, and experiment that produced it. And this isn’t merely an academic concern. Reproducibility makes models easier to debug, audit, compare, retrain, and ultimately trust in production. > Notes: Detailed Presentation Notes — SHAP: Making the Churn Model Explainable Opening: Prediction versus explanation Up to this point, we’ve focused primarily on whether our churn model makes good predictions. But once a model moves toward production, another question becomes important:  Why did the model make that prediction?  Suppose our XGBoost model tells us that a particular customer has a 78% probability of churn. That’s useful, but a retention manager will immediately want to know: Why is this customer considered high risk?  This is where SHAP—SHapley Additive exPlanations— becomes useful. SHAP provides a way to estimate how much each feature contributes to a model’s prediction. Importantly, we can use it at two different levels, both of which are illustrated here. The left chart gives us a global explanation of the model. The right chart gives us a local explanation for one customer.  Left: SHAP Summary Plot — Understanding the model globally Let’s begin with the summary plot. Here we’re asking: Across all our customers, which features most influence the model’s predictions? The horizontal axis shows mean absolute SHAP value. Conceptually, the larger this value, the more that feature tends to move predictions away from the model’s baseline prediction. The most influential feature in this example is recency_days—how long it has been since the customer’s recent activity. Its mean SHAP magnitude is approximately 0.48. The next most important features are total spend, number of transactions, and average transaction value.  Notice that recency_days has considerably more influence than the other variables. That’s an important distinction because importance and direction are different concepts.  What should we learn from global SHAP? This global view helps us understand what the model has learned. For example, if we expected recent customer activity to be strongly related to churn and recency_days appears near the top, that may be reasonable. But imagine that a variable we considered irrelevant suddenly became the most influential feature. That could reveal: a data-quality problem, unintended leakage, an unexpected proxy variable, or a relationship we hadn’t previously recognized. So explainability isn’t simply about creating nice visualizations for business users. It can also help us debug and validate the model itself.  Right: SHAP Waterfall Plot — Explaining one prediction Now we move from the entire population to one individual customer. The red bars push the prediction toward greater churn risk. For this customer, recency_days contributes the largest upward push. Customer tenure, email engagement, recent application logins, and age provide smaller contributions that reduce the model’s churn estimate.  SHAP therefore turns a single number—Churn probability = 78%—into something closer to an explanation: These particular characteristics pushed the model toward that prediction, while these other characteristics pushed it in the opposite direction.  Global versus local explainability This gives us a useful distinction for students: Global explanation: “What generally drives this model?” That’s the left chart. Local explanation: “Why did the model make this particular prediction?” That’s the right chart. Both are useful, but they answer very different questions. A data scientist might use global explanations to understand overall model behavior. A retention specialist might care much more about the local explanation for a specific customer.  How this becomes useful operationally Imagine that our retention team receives a list of 5,000 customers predicted to have high churn risk. Now the prediction becomes easier to investigate and potentially act upon. The retention team might decide that customers whose risk is primarily associated with declining engagement receive one intervention, while customers showing different patterns receive another.  So explainability can help connect prediction to business action.  Important caution: SHAP is not causal This is probably the most important caveat on the slide.  SHAP tells us: How features contributed to the model’s prediction. It does not tell us:  What caused the customer to churn.  For example, if low engagement strongly contributes to churn predictions, we cannot conclude from SHAP alone that increasing engagement will necessarily prevent churn. There may be other variables driving both behaviors. Suppose we discover that predictions are being heavily influenced by a variable we never expected to matter. We should ask why. Or suppose a feature acts as a proxy for something inappropriate or undesirable. Again, the explanation gives us a reason to investigate. Without explainability, we might see an AUC of 0.76 and conclude: “The model performs well enough.” With explainability, we can ask the deeper question: “What has the model actually learned to make those predictions?” That is often just as important as the performance metric. Connection to our broader XOps workflow This slide also connects several pieces of the lecture. So we’re gradually moving beyond simply asking: “Can we train a model?” toward the more important production question:  “Can we build a model that performs well, can be reproduced, can be understood, and can be responsibly operated?”  Key takeaway I would leave students with this distinction: Predictive performance tells us whether the model works. SHAP helps us understand how the model is using its features to produce those predictions.  And remember: SHAP explains the model—not necessarily the world. ## Slide 13
- What is SHAP?
> Notes: Summary So if a student remembers only one thing, I would make it:  A SHAP value tells us how much a feature pushed a particular prediction above or below a baseline, with the credit allocated by considering that feature across different combinations of the other features. One important caveat is worth teaching alongside this: SHAP explains the model, not necessarily reality. A large SHAP value means a feature strongly influenced the model’s prediction; it does not establish that the feature caused the real-world outcome.  OpeningWe just saw that our churn model predicts 0.78 for customer 78246. The obvious next question is why. SHAP answers that. The name stands for SHapley Additive exPlanations: for any single prediction, it tells us how much credit each feature deserves. 1 – Game-theory rootsThe idea comes from cooperative game theory, from work Lloyd Shapley did in the 1950s. He asked how you split a team's payout fairly when each player contributed a different amount. His answer: try the players in every possible order, record how much the payout goes up when each one joins, and average that over all the orders. SHAP treats the model's prediction as the payout and the features as the players. One thing the pie on the slide hides: in SHAP a player can have a negative share. A feature can pull the prediction down, the way long tenure lowers churn risk for this customer. 2 – Adds up exactlyThis is what makes SHAP practical. We start from the base value, the model's average prediction across all customers, which is 0.40 here. Then we add each feature's SHAP value. For this customer the features that raise risk add up to +0.53, the ones that lower it add up to −0.15, and 0.40 + 0.53 − 0.15 lands exactly on 0.78. That's the equation at the bottom: the prediction equals the expected prediction plus the sum of the SHAP values. Nothing is left unexplained, so you can show a stakeholder a waterfall where every point of risk is accounted for. 3 – Local to globalEach customer gets their own explanation; that's the local view, and it's the waterfall we saw earlier. If we take the absolute SHAP values for every customer and average them feature by feature, we get global importance, which is the summary plot on the previous slide. We take absolute values because otherwise positive and negative effects would cancel out, and a feature that matters a lot in both directions would look unimportant. Keep in mindTwo cautions before anyone takes these charts to the business: SHAP explains the model, not the world. If recency_days has a big SHAP value, the model relies on it heavily. That doesn't mean changing recency will change whether a customer actually churns. Causal claims need experiments or causal methods. Correlated features split credit. Our transaction features move together, so SHAP may divide their credit in ways that look arbitrary. Read them as a group rather than ranking them against each other.  Here are three references, ordered from gentlest to most rigorous: Christoph Molnar, Interpretable Machine Learning, chapter "SHAP." A free online textbook chapter and the best conceptual introduction. It builds up from Shapley values, then covers KernelSHAP and TreeSHAP and how to read the plots. It's also honest about limitations, such as correlated features and causal misreadings. It's the right assignment for students before the lab. SHAP documentation, "An introduction to explainable AI with Shapley values." The hands-on tutorial from the library's own docs. It walks through code for the exact plots on your slide: waterfall plots, which show how SHAP gets from the base value to the model's prediction, and beeswarm plots, which show direction as well as magnitude. That makes it a good companion for students fixing the waterfall issues we discussed. Scott Lundberg and Su-In Lee, "A Unified Approach to Interpreting Model Predictions," NeurIPS 2017. The original paper that introduced SHAP. It shows how SHAP unifies six earlier explanation methods under one framework with guaranteed properties. It's the citation for your slides and a good read for advanced students. If you want a fourth for tree models specifically, the follow-up paper by Lundberg et al., "From local explanations to global understanding with explainable AI for trees" (Nature Machine Intelligence, 2020), introduced the fast exact TreeSHAP algorithm used with XGBoost.

## Slide 19
- Common model development mistakes
> Notes: OpeningEvery mistake on this slide has the same symptom: the model looks better in development than it really is. None of them crash your code or throw an error. You find out in production, when the numbers don't hold up. That's what makes them dangerous, and it's why each row pairs the mistake with what it costs and how to prevent it.  1. Cherry-picked thresholdA classifier outputs a probability, and we choose a cutoff, say 0.4, to turn it into "churn" or "no churn." If you try thresholds against the test set and keep the one that scores best, the test set has become training data. Your reported precision and recall are now optimistic. Choose the threshold on validation data, or better, from business costs: what does a missed churner cost, and what does an unnecessary retention offer cost? Then score the test set once.  2. Overfitting to validationThis one is subtle. You do everything "right": train on training data, tune on validation. But after fifty rounds of tuning against the same validation set, you've started fitting its quirks. Validation looks great, and production doesn't. The fix is cross-validation, nested if you're tuning hyperparameters, so no single split drives decisions, plus a test set nobody touches until the end. Remember the MLflow slide: a 0.009 AUC gain on one split is exactly where this bites.  3. Data leakageLeakage means the model sees information at training time that it won't have at prediction time. Two common forms: Future data in features. For churn, a feature like "support tickets in the last 30 days," computed after the customer already cancelled, practically gives away the answer. Preprocessing fit on everything. Fitting a scaler or imputer on the full dataset before splitting lets test-set statistics leak into training. Leakage produces the most dramatic gap between offline and production of anything on this slide. Fix it by building every feature "as of" the prediction date, splitting by time, and fitting all preprocessing on the training split only.  4. Ignoring class imbalanceIn our churn data, about 20% of customers leave. A model that predicts "nobody churns" is 80% accurate and completely useless. Accuracy hides the misses. Handle it with class weights or resampling, and report metrics that focus on the minority class: recall, precision, PR-AUC. One caveat that connects to our evaluation slide: class weighting improves ranking but distorts probabilities. Our weighted model predicted 41% average churn against 20% actual. If the business uses the probabilities themselves, recalibrate afterward.  5. Skipping error analysisA single overall metric averages away the story. Pull up the misclassified customers and slice them by segment: region, plan type, tenure. You'll often find the model fails systematically for one group, such as new customers with little history. That's both a performance problem and a fairness problem. The fix is iterative: review errors by segment, then improve the data or features where the model is weakest. Closing If you remember one rule from this slide: the test set is for measuring, never for deciding. Every decision (thresholds, features, hyperparameters) happens on training and validation data. The test set gets used once, at the end, to tell you the truth.
