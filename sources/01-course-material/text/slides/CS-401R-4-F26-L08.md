> Notes: Presentation Notes — Model Development II: Retrieval-Augmented Generation Opening/connection to Model Development I In the previous lecture, we looked at the broader model-development spectrum: prompt engineering, RAG, fine-tuning, custom model training, and ultimately custom architectures. Today we’re going deeper into one of the most important techniques for enterprise generative AI: Retrieval-Augmented Generation, or RAG.  The basic motivation is simple: A foundation model may be very capable, but it doesn’t automatically know an organization’s private, current, or specialized information. RAG addresses that problem by retrieving relevant information at runtime and giving it to the model as context. The core idea Suppose a user asks a question about information contained in thousands of company documents. Without RAG, the LLM can answer only from information already encoded in its parameters plus whatever we put directly into the prompt. With RAG, we add a retrieval system in front of the LLM.  OpeningA RAG system is really two separate processes that share one component. The top half runs ahead of time and prepares our knowledge. This is similar to the data pipeline you are creating for Lab 2 used in classical ML models. The bottom half runs every time a user asks a question. The vector store in the middle is where they meet. Most RAG problems come from one half or the other, so it pays to keep them distinct.  1 – Ingestion (top, offline)Ingestion turns a pile of documents into something we can search by meaning. Documents: for NorthStar that's the product catalog, return policies, help pages: whatever we want the assistant to know. Parse: extract clean text. Strip headers, navigation menus, and boilerplate. Messy text here becomes messy answers later. Chunk: split the text into short passages, often a few hundred tokens with some overlap. This is one of the most important design choices in RAG:  Chunks too big bury the relevant sentence in noise. Chunks too small lose context: half a policy with none of its conditions. Embed: an embedding model turns each chunk into a vector, a list of numbers that captures its meaning. Passages about similar topics end up near each other, even if they use different words. Index: we store the vectors in the vector store, together with the original chunk text and metadata such as source, date, and who's allowed to see it. The metadata matters: it's what lets us cite sources and filter results, for example by date or user permissions. One operational point: ingestion is never "done." When a policy changes, we re-index it. Otherwise, the assistant will confidently quote last year's return window.  2 – Query and response (bottom, online)Now a customer asks: "What is the return window?" Embed: we turn the question into a vector using the same embedding model we used for the documents. That's the dashed line. If the models differ, the question and the documents live in different vector spaces, and retrieval returns nonsense without any error message. That also means switching embedding models requires re-indexing everything. Retrieve: the vector store finds the chunks closest in meaning to the question, the top-k, often 3 to 10. Many systems add a reranking step here to put the best matches first. Augment: we build the prompt: instructions, the user's question, and the retrieved chunks. Good instructions say "answer only from the provided context, cite your sources, and say so if the answer isn't there." Generate: the LLM writes the answer from those chunks, not from its training memory, and we return it to the user with sources they can check.  Why this design works The model can answer from information it was never trained on, including information that changed this morning. Answers can be traced back to a source document. Updating knowledge means re-indexing documents, not retraining a model.  Connecting to evaluationThe two halves also map onto how things fail: Retrieval failures: bad chunking, weak embeddings, a stale index, or top-k too small. Context precision and recall catch these. Generation failures: the LLM ignores or embellishes the chunks it was given. Faithfulness and answer relevancy catch these. When an answer is wrong, the first question is always: did we retrieve the right evidence?

The other two improve the retrieval side. An example Take the Northstar support assistant answering a return-policy question: RAG alone: it retrieves policy P-0023 and answers correctly, but the tone varies, the format changes from answer to answer, and it sometimes adds details from general knowledge. Fine-tuning alone: it sounds like a Northstar agent every time, but it quotes whatever policy it saw during training. When the policy changes from 30 days to 15, it is wrong until you retrain. Both: RAG fetches the current policy, and the fine-tuned model answers in Northstar's voice, in the standard format, citing only the retrieved text. Why the split works Facts change often, and behavior changes rarely. Updating a document in the knowledge base takes minutes. Retraining a model takes days. Fine-tuning is a poor way to store facts. The model can't cite where a fact came from, can't forget an outdated one, and may blend it with others. RAG can't change habits. Retrieved text gives the model information, but it doesn't change how the model writes or reasons. A useful line for students: RAG is an open-book exam, and fine-tuning is the studying beforehand. The best result comes from a student who has studied and also has the book. How it's done in practice Build the RAG pipeline first with a standard model, and measure it. Find the failures that better prompts and better retrieval can't fix. Fine-tune the generator on examples that look like production: a question, the retrieved passages, and the ideal answer. Include some examples with irrelevant passages, so the model learns to ignore noise and to say when the answer isn't there. Re-run the same evaluation to confirm that the fine-tuned model improved faithfulness and didn't hurt anything else. ## Slide 3
- Why RAG? The fundamental Problem it solves
> Notes: Presentation Notes — Why RAG? The Fundamental Problem It Solves Opening: The knowledge problem This slide explains why RAG exists in the first place. Foundation models are extremely capable, but enterprise applications expose a fundamental limitation: the model’s internal knowledge is not the same thing as the organization’s current knowledge.  Suppose a customer asks: “What is NorthStar’s current return policy?” A foundation model may be perfectly capable of understanding the question and writing a fluent response. But that doesn’t mean it actually knows NorthStar’s current policy. That’s the problem RAG is designed to solve.  The left side — Why the foundation model alone isn’t enough There are four related problems. First, knowledge has a cutoff. A foundation model learns information during training. Information created or changed afterward isn’t automatically incorporated into its parameters. NorthStar might change its return policy this morning, but the model doesn’t magically learn about that change. Second, the model doesn’t automatically have access to private enterprise data. NorthStar’s internal policies, customer histories, product information, contracts, and operational data may never have appeared in the model’s training data. Third, models can generate unsupported answers. If the model doesn’t know the policy, it may still produce a plausible-sounding response. In this example, it confidently invents details about free return shipping and loyalty members. This is especially dangerous in enterprise applications because fluency can be mistaken for factual accuracy. Fourth, retraining isn’t a practical way to keep knowledge current. We wouldn’t want to fine-tune or retrain the model every time NorthStar changes a policy, introduces a product, or updates a promotion. So the architectural problem is: How do we combine the reasoning and language capabilities of the foundation model with information that is private, current, and constantly changing?  The right side — RAG’s answer RAG separates knowledge storage from language generation.  Instead of trying to put NorthStar’s policies into the model’s weights, we maintain them in an external knowledge source. When the customer asks about the return policy, the retrieval system searches NorthStar’s policy documents and identifies the relevant passage. That passage is then placed into the LLM’s context along with the customer’s question. The model’s task changes from: “Tell me NorthStar’s return policy from whatever you happen to know.” to something much safer and more constrained: “Using this retrieved NorthStar return policy, answer the customer’s question.” That is the central idea behind RAG.  Retrieval happens at inference time Notice when this occurs: at inference time. Every time a question arrives, the system can retrieve the information relevant to that particular question. Tomorrow, if NorthStar changes the policy, we update the document and its retrieval index. We don’t need to retrain the LLM. The next query can retrieve the new information.  This gives us an important architectural principle: Keep rapidly changing knowledge outside the model. Retrieve it when needed. What RAG does—and doesn’t—solve There is one qualification worth emphasizing. RAG can reduce hallucination by grounding the model in retrieved evidence, but it doesn’t eliminate hallucination automatically. A RAG system can still fail if: it retrieves the wrong document, it misses the relevant document, the source document itself is outdated, the prompt doesn’t tell the model to rely on the evidence, or the model misinterprets the retrieved information. So RAG introduces a new engineering requirement: retrieval quality matters just as much as generation quality. A useful mental model  I would summarize the architecture for students this way: Without RAG: Question → LLM → Answer from internal model knowledge  With RAG: Question → Retrieve evidence → Give evidence to LLM → Grounded answer The LLM remains valuable because it can interpret the question, reason over the retrieved material, synthesize information, and communicate the answer naturally. But we stop asking the LLM to serve simultaneously as our reasoning engine and enterprise database.  Connection to fine-tuning This also reinforces our distinction from the previous lecture. If the problem is: “The model doesn’t know NorthStar’s current return policy.” that’s primarily a RAG problem. If the problem is: “The model knows the policy, but it consistently responds in the wrong format or doesn’t follow our required customer-service behavior.” that may become a prompting or fine-tuning problem.   So: RAG supplies current knowledge. Fine-tuning can adapt recurring behavior.  Key takeaway The central message of this slide is: Don’t force frequently changing enterprise knowledge into the model. Keep that knowledge in systems designed to store and update information, retrieve relevant evidence at inference time, and let the foundation model reason over it. That’s why RAG has become such an important enterprise AI architecture: it combines the language and reasoning capabilities of foundation models with the private, current, and controllable knowledge of the enterprise.

## Slide 4
- RAG vs. Fine-tuning: The decision framework
> Notes: Presentation Notes — RAG vs. Fine-Tuning: The Decision Framework This slide provides a practical way to decide among prompt engineering, RAG, fine-tuning, or a combination of RAG and fine-tuning. The framework asks two basic questions: Does the application need external knowledge that changes frequently?Does the application require specialized, task-specific behavior?  Those two questions give us the four quadrants.  1. Prompt Engineering Only Start in the lower-left corner. If the required knowledge is relatively stable and the foundation model already has the capabilities we need, prompt engineering may be sufficient. For example, if we’re asking the model to summarize, rewrite, classify something simple, or perform a general reasoning task, there may be no reason to introduce retrieval or modify the model. This reinforces our general design principle: Start with the simplest architecture that can satisfy the requirements. Don’t build a RAG pipeline or fine-tune a model unless the application actually needs it. 2. RAG — When knowledge is the problem The upper-left quadrant represents RAG. RAG is appropriate when the model needs access to knowledge that lives outside the model—for example: product catalogs, policy documents, FAQs, customer histories, or other proprietary enterprise information. RAG becomes particularly attractive when that information changes frequently or when we need to show where an answer came from. The key idea is: If the problem is missing or changing knowledge, retrieve the knowledge rather than retraining the model. 3. Fine-Tuning — When behavior is the problem The lower-right quadrant represents fine-tuning. Here the issue isn’t primarily that the model lacks information. Instead, we need it to behave differently or perform a specialized task more consistently. Perhaps we need a particular tone, output format, classification behavior, terminology, or reasoning pattern, and prompting alone isn’t sufficiently reliable. If we also have a substantial collection of high-quality examples demonstrating the desired input-output behavior, fine-tuning becomes a candidate. So the shorthand distinction remains: RAG changes what information the model receives. Fine-tuning changes the behavior we’re trying to elicit from the model. 4. RAG + Fine-Tuning — When we need both The upper-right quadrant is where sophisticated enterprise systems may eventually end up. Suppose we need current proprietary information and highly specialized behavior.  Then RAG and fine-tuning aren’t competitors. They solve different parts of the problem. RAG might retrieve the current product catalog, customer history, or policy information. A fine-tuned model might then use that information while consistently following a specialized response structure, terminology, or organizational style. Conceptually: RAG supplies the right knowledge → Fine-tuned model applies the desired behavior Applying the framework to NorthStar Offer Generation Now consider our NorthStar Offer Generation application. Why are we choosing RAG rather than fine-tuning as our primary approach? First, the underlying knowledge changes frequently. Products, prices, promotions, inventory, and offers can change constantly. Second, offer generation requires customer-specific context. Different customers have different histories, preferences, and behaviors. Third, we may want source transparency—the ability to connect an offer to the information used to generate it. Fine-tuning is not a particularly good mechanism for those requirements. Imagine retraining the model every time NorthStar launches a new promotion. That’s exactly what we want to avoid. Instead: Customer request → Retrieve current customer context + current product information → Generate the offer Could NorthStar eventually use fine-tuning too? Yes. Suppose our RAG system retrieves excellent information, but evaluation shows that the model still doesn’t consistently produce offers in NorthStar’s preferred retail tone, structure, terminology, or format. At that point, fine-tuning could complement RAG. We would still use RAG for the changing facts. Fine-tuning would help reinforce the desired behavior. So NorthStar could eventually move from: RAG to: RAG + Fine-Tuning without abandoning the retrieval architecture. One qualification about the diagram The two axes are best treated as a decision heuristic rather than a rigid rule. For example, fine-tuning can be useful even when knowledge doesn’t change frequently, and RAG can be useful for relatively stable information when provenance or access to proprietary documents matters. The real diagnostic questions are: Is our problem primarily missing knowledge? → consider RAG.  Is our problem primarily inconsistent or specialized behavior? → consider fine-tuning.  Do we have both problems? → consider RAG + fine-tuning.  Do we have neither? → start with prompt engineering.  Key takeaway The most important message from this slide is: Don’t choose RAG or fine-tuning because one technique is more sophisticated. Diagnose what the application is missing. A useful shorthand is: Prompt Engineering = instruct the modelRAG = supply external knowledge and contextFine-Tuning = reinforce specialized behaviorRAG + Fine-Tuning = combine changing knowledge with specialized behavior  For NorthStar Offer Generation, the immediate challenge is current, proprietary, customer-specific knowledge. That’s why RAG is the appropriate next step.  Notes: "The most common mistake: teams fine-tune a model on their knowledge corpus when RAG would have been faster, cheaper, and more maintainable. Fine-tuning encodes knowledge in the model's weights — which means you need to fine-tune again when that knowledge changes. RAG externalizes knowledge — you update the index, not the model." For NorthStar, the product catalog has 12,000 SKUs that change frequently. RAG is clearly the right choice.

## Slide 5
- RAG AWS Architecture Diagram
> Notes: OpeningThis is the RAG pattern we just walked through in the first slide, but this time built from AWS managed services. The shape is the same: an ingestion process on top that runs ahead of time, and a query path on the bottom that runs for every request.  1 – Ingestion (top)Our source documents (product catalog, return policies, help articles) live in an Amazon S3 bucket. That bucket is the Knowledge Base's data source. When we run a sync, Amazon Bedrock Knowledge Bases runs the ingestion pipeline for us: Chunk: it splits each document into passages. Embed: it sends each passage through an embedding model, here Amazon Titan Text Embeddings, to turn it into a vector. Index: it writes the vectors, the passage text, and metadata into Amazon OpenSearch Serverless, our vector index. In a hand-built system, each of those arrows is code you write, test, and maintain. Here they're configuration: you choose the data source, the chunking strategy and the embedding model, and Bedrock runs the pipeline. When documents change, you update S3 and sync again. No retraining.  2 – Query path (bottom)Follow the numbers. Request. The user's question arrives at API Gateway, the HTTPS front door, which handles authentication and throttling. It invokes a Lambda function that orchestrates the rest.  2. Retrieve. Lambda calls the Knowledge Bases Retrieve API. The Knowledge Base embeds the question with the same embedding model used at ingestion, runs a vector search in OpenSearch, and returns the top-k matching chunks. That shared embedding model is the rule from our earlier RAG slide. Here the managed service enforces it for us.  3. Generate. Lambda sends the question plus those chunks to a Bedrock model such as Claude, with instructions to answer only from the context. Bedrock Guardrails wraps that call. It screens the user's input for off-topic or harmful requests, and it screens the model's output by filtering content, redacting personal information, and blocking denied topics.  4. Respond. The grounded answer flows back through Lambda and API Gateway to the user.  A practical aside: Bedrock also offers a single RetrieveAndGenerate API that does steps 2 and 3 in one call. Splitting them, as shown here, gives you control: you can log the retrieved chunks, rerank them, or evaluate them separately.  Why this pattern Serverless end-to-end: no GPUs or servers to manage, and you pay per request, per token, and per document indexed. Clear failure boundaries: retrieval problems live in steps 1–2 and the index; generation problems live in step 3. That maps directly onto RAGAS's retrieval and generation metrics.  Transition to chunkingOf all the settings in this architecture, one quietly has the biggest effect on answer quality: chunking. Chunking decides what the retriever can ever find. Split a return policy in the wrong place, and the rule lands in one chunk, and its exception in another, and no model can put them back together. So let's open that box and look at chunking strategies in detail.

## Slide 6
- Document chunking strategies
> Notes: Opening (15 sec)Before a RAG system can retrieve anything, someone must decide how to split the documents. It sounds like plumbing, but chunking is one of the biggest levers on retrieval quality, and one of the first things to tune when RAG answers are poor.  The chunking problem (30 sec)Point to the spectrum at the top. There's a tension here. Chunks that are too small lose meaning: a sentence cut off from its context can't answer a question on its own, so retrieval misses it. Chunks that are too large drag in irrelevant text, dilute the embedding, slow retrieval, and waste the model's context window. The goal is a chunk that is one coherent idea: small enough to be precise, large enough to stand alone.  1. Fixed-size (40 sec)The naïve baseline: split every N tokens, typically a few hundred, with some overlap between neighbors. It's fast and needs no understanding of the document. Point to the red cuts. The chunker doesn't know where sentences end, so cuts land wherever the token count runs out. Two of these cuts split a paragraph mid-thought; one happens to land on a clean break. That's pure luck. Overlap is the patch: repeating a bit of text across the boundary so a split idea still appears whole in one chunk, at the cost of some duplication. NorthStar uses this for customer FAQs. Each FAQ entry is short and uniform, so most fit in a single chunk anyway and there's little structure to lose.  2. Semantic (35 sec)Split at natural boundaries: paragraphs, sections, or sentences. Notice the chunks are now different sizes, because meaning doesn't come in equal token counts. Each chunk holds a complete thought, so coherence is high. NorthStar uses this for return policy documents. A policy is written in paragraphs that each cover one rule, so paragraph boundaries line up with the questions customers ask: "Can I return an opened item?" maps to one paragraph.  3. Document-aware (40 sec)Use the document's own structure (headers, bullets, tables) to define chunks. This goes a step beyond semantic chunking because the author has already told you where the boundaries are. Point to the catalog. Every SKU becomes one chunk carrying all of its attributes. That matters: if price landed in one chunk and dimensions in another, a question like "Is the 40-liter pack under $150?" would need two lucky retrievals. It also preserves hierarchy. Each chunk can carry its header path (catalog, category, SKU) as metadata, which helps retrieval and filtering.  Semantic chunking follows the meaning of the content (especially useful for documents with weakly structured text); document-aware chunking follows the document's explicit structure.  4. Hierarchical (40 sec)Two layers: summary chunks on top, detail chunks underneath. Retrieval first searches the summaries to find the right area, then expands to the details only if needed. NorthStar uses this for the product catalog at the category level: "What hiking gear do you carry?" is answered by the category summary, while "What's the weight of this tent?" drills down to one product. It handles both broad and specific questions without forcing one chunk size to serve both.  Key takeaway (20 sec)There's no single best strategy. Match the chunking to the document type. NorthStar uses four different strategies across its corpus, and that's normal for a production system. Start simple, measure retrieval quality, and move up in sophistication where the evaluation shows it pays off. Stress that the chunk counts and sizes are illustrative.  Discussion prompt (optional)"Think about a document type you work with: contracts, lecture notes, code, email threads. Which strategy fits, and where would fixed-size chunking break it?"  Anticipated questions "What chunk size should I start with?" Commonly a few hundred tokens with 10–20% overlap as a baseline. Then tune it against a retrieval evaluation set rather than by intuition, because the right size depends on the embedding model and the questions users ask. "Isn't semantic chunking just splitting on paragraphs?" The simple version is. More advanced versions embed sentences and split where the topic shifts, measured by a drop in embedding similarity between neighboring sentences.  "How do tables survive chunking?" Badly, with fixed-size chunking: rows get split from their headers. Document-aware chunking keeps a table together or converts each row to a self-describing text record.  "Doesn't hierarchical chunking cost more?" Yes. You generate and store summaries, often with an LLM, and retrieval takes two steps. It's worth it for large corpora where both broad and specific questions are common. ” XOps angle?" Chunking is part of the ingestion pipeline and needs versioning like any other transformation. Changing the strategy means re-chunking and re-embedding the corpus, so treat it as a tracked configuration and evaluate before rolling it out.  RAG Retrieval Metrics: Recall@K: fraction of relevant chunks that appear in the top-K results — measures whether the retriever found the right information at all Precision@K: fraction of the top-K results that are actually relevant — measures how much noise the retriever returns MRR (Mean Reciprocal Rank): average of 1/rank for the first relevant result — penalizes relevant chunks buried at rank 5 vs rank 1 NDCG@K: discounted cumulative gain, handles graded relevance where one chunk is more relevant than another Context Precision: of the chunks actually sent to the model, what fraction were relevant — measures retrieval efficiency  Source: https://www.frontierengg.com/lessons/rag-systems/retrieval-quality-metrics?utm_source=chatgpt.com

## Slide 7
- Embedding Models: Turning Text into searchable vectors
> Notes: Opening (15 sec)Last slide we cut documents into chunks. Now we need a way to find the right chunk for a question, even when the question uses completely different words than the document. That's what embeddings do: they turn text into numbers that capture meaning.  What is an embedding? (40 sec)Point to the top right. An embedding model reads a piece of text and outputs a vector, a list of numbers, typically hundreds to a few thousand long. Each number on its own means nothing you can interpret. Together they place the text at a point in a high-dimensional space. The key property is that the model is trained so that texts with similar meanings land close together. "Trail running shoe" and "lightweight sneaker for jogging" share almost no words, but their vectors end up near each other. That's the difference from keyword search.  Walking the embedding space (60 sec)Point to the plot. Each dot is a NorthStar product description, squashed from over a thousand dimensions down to two so we can see it. Nobody told the model about product categories, yet electronics, apparel and home goods form their own clusters. The model learned that earbuds and streaming sticks are "about" similar things. (t-SNE stands for t-distributed Stochastic Neighbor Embedding. It’s a dimensionality-reduction technique designed primarily for visualizing high-dimensional data in 2D or 3D.)  Now the query: "looking for comfortable running shoes." We embed it with the same model, and it lands at the edge of the apparel cluster. Retrieval is now just geometry: find the nearest points. The top three are a road running shoe, a trail runner, and running socks. The socks are a useful teaching moment. They're semantically close but not exactly what was asked for, which is why production systems often add a reranking step after retrieval. Caution the class about the axes. t-SNE preserves who is near whom, not actual distances, so don't read meaning into the x and y positions. Also stress that this plot is illustrative.   Choosing a model (50 sec)Point to the table. The trade-offs are dimensions, cost, and quality. More dimensions can capture finer distinctions but cost more to store and search: every vector in the index is that long. OpenAI's large model is the quality leader here; the open-source MiniLM is free and runs anywhere, but its quality is only acceptable, and it's best suited to short English text. The quality ratings are relative, and every team should test candidates on its own data. Public leaderboards like MTEB (Massive Text Embedding Benchmark) are a starting point, not a verdict. (https://github.com/embeddings-benchmark?utm_source=chatgpt.com)  NorthStar's choice (30 sec)NorthStar uses Amazon Titan Text Embeddings v2. Quality is good for retail product text, and the cost is low, but the deciding factors are architectural. It's native to Bedrock, so it plugs into the rest of the AWS stack without extra infrastructure, and no customer or product data leaves AWS. For many enterprises, data residency settles the choice before quality benchmarks do.  The consistency rule (30 sec)Point to the red banner. This rule bites teams in production. The same model must embed the documents at index time and the queries at search time. Vectors from different models live in different spaces, so comparing them is like measuring distance between points on two unrelated maps. It fails silently: the search still returns results; they're just wrong. The consequence: switching embedding models means re-embedding and rebuilding the entire index. Choose deliberately.  Anticipated questions "How is closeness measured?" Usually cosine similarity, the angle between two vectors, which ignores vector length and focuses on direction.  "Are more dimensions always better?" No. Gains flatten out, while storage and search costs grow with every dimension. Titan v2 and OpenAI's v3 models let you choose a smaller output size, trading a little quality for a cheaper index.  "Can I fine-tune an embedding model?" Yes, for specialized vocabulary like part numbers or medical terms. It still triggers the consistency rule: a fine-tuned model means a new index.  "What about multilingual queries?" You need a multilingual model. An English-only model like cohere.embed-english-v3 won't place a Spanish query near its English equivalent.  ”XOps angle?" Pin the embedding model version as part of the index's metadata and treat a model change like a schema migration: re-embed into a new index, evaluate retrieval quality, then cut over, with the old index kept for rollback.

## Slide 8
- Vector Search: The Retrieval Engine
> Notes: Opening (15 sec)We have chunks, and we have embeddings. Now we need somewhere to store millions of vectors and a way to find the closest ones to a query in milliseconds. That's the vector store, the retrieval engine at the center of RAG.  Walking the pipeline (2 min)Follow the numbers on the slide.  Step 1, embed the query. A customer types "comfortable running shoes, in stock." We embed that text with Titan v2, the same model we used to index the catalog. That's the consistency rule from the last slide in action.  Step 2, filter. Before any vector math, OpenSearch applies the metadata filter: in stock, and in the Footwear category. That cuts 48,000 products down to about 1,850 candidates. Point out the word "in stock" in the query. The embedding can capture "running shoes" as meaning, but it can't know current inventory. Hard facts like stock, price, and category belong in structured fields, not in the vector.  Step 3, k-NN search. Now OpenSearch finds the vectors closest to the query among the candidates. In the cube, purple dots passed the filter, hollow ones didn't, and the red lines connect the query to its nearest neighbors. This returns a top-K list, typically 5 to 20.  Step 4, rerank. Vector search is fast but approximate in its judgment of relevance. A reranking model then looks at the query and each candidate together and reorders them more precisely. It's too slow to run on the whole catalog, but cheap enough for 10 results.  Step 5, top 3 to the LLM. Only the best three go into the prompt, with their metadata: product ID, price, stock. The LLM on Bedrock writes the answer grounded in those facts.  Why filter first? (30 sec)Filtering before the search guarantees that everything returned is eligible. The alternative, searching first and filtering afterward, can go wrong. If eight of your top ten nearest neighbors are out of stock, you're left with two results. OpenSearch supports both, and choosing between them is a real design decision.  Choosing a vector store (50 sec)Point to the table. For NorthStar, OpenSearch wins on fit rather than raw performance. It's AWS-native, so it shares security, networking, and IAM with the rest of the stack; it scales as a managed service; and it has strong metadata filtering, which we just saw is essential. The others have their places. Pinecone is a strong managed product, but it's another vendor and another place your data lives. pgvector is attractive if you already run Postgres, at the cost of operating it yourself. FAISS and Chroma are great for notebooks and prototypes, which is often where your first RAG experiment should start, but they aren't production services on their own.  Index design (40 sec)Point to the schemas. Each index holds the vector plus the fields you need to filter and display. The product catalog carries price, category and stock, one document per SKU, matching the document-aware chunking from earlier. The policy index stores chunks with their document name and section, so answers can cite where the chunk came from. Stress the design principle: decide at index design time what you'll need to filter and cite, because adding a field later can mean reindexing.  Key takeaway (15 sec)Good retrieval is layered: structured filters for hard constraints, vector search for meaning, reranking for precision, and only the best few results reach the LLM. Remind the class that the counts and scores are illustrations.  Discussion prompt (optional)"What other NorthStar queries mix meaning and hard constraints? Which parts belong in the vector, and which belong in a metadata filter?"  Anticipated questions "Does k-NN compare the query against every vector?" Not at scale. ## Slide 9
- Reranking: Improving retrieval precision
> Notes: Opening (15 sec)Vector search is good at finding things that sound like the question. That's not the same as finding things that answer the question. Reranking is how we close that gap, and it's often the cheapest big improvement you can make to a RAG system.  Two-stage retrieval (60 sec)Point to the funnel. Retrieval is split into two stages because we can't afford to be both fast and precise over the whole corpus. Stage 1 is the k-NN search from the last slide. It uses a bi-encoder: queries and documents are embedded separately, and document vectors are computed once at indexing time. That's what makes it fast, but the model never sees the query and the document side by side. It compares two summaries of meaning. Stage 2 is a cross-encoder. It reads the query and each candidate together and outputs a relevance score. It can notice that a passage mentions electronics but never mentions returns. That's far more accurate, but it has to run once per candidate at query time, so we only give it the top 20, never the whole index. The cost is typically 50 to 200 milliseconds.  An analogy: hiring. Stage 1 is screening résumés by keyword match against a job description. It's cheap, it scales to thousands of applicants, and it's rough. Stage 2 is the interview. It's expensive, so you only do it for the shortlist, but it's where you discover that a candidate listed "Python" and has never actually shipped anything. An interview can't rescue a great candidate who got filtered out at the résumé stage. That's the recall ceiling.   The comparison (75 sec)Point to the query: "return policy for electronics purchased online." Walk the left column. Embedding similarity ranked a buying guide first. It's full of the right words, electronics and ordering online, but contains no return information. Third place is a genuine return policy, but for in-store apparel. Only one of three results is useful, so precision@3 is 33%. The LLM would get two distracting passages and could easily blend apparel rules into an electronics answer.  Now the right column. The cross-encoder re-scored all 20 candidates. The electronics returns section rises to the top, and it pulls up two sections that were further down the list: returns for online orders, and the restocking fee for opened electronics. All three are relevant, so precision is 100%. Stress this point: reranking can only reorder what stage 1 found. The good passages were already in the top 20. That's why stage 1 is tuned for recall, casting a wide net, and stage 2 for precision.  Across 100 queries (30 sec)Point to the chart. One example is anecdote; this is the evaluation view. Without reranking, most queries get one or two relevant results in the top 3. With reranking, the distribution shifts right: most queries get all three. The mean moves from 54% to 83%. Stress that these numbers are illustrations. The habit to teach is measuring precision@K on a test set of real queries before and after.  Model options (30 sec)Cohere Rerank is available on Bedrock, so for NorthStar it's one more API call inside AWS. Open-source cross-encoders from HuggingFace avoid per-call fees but require you to host a model yourself. The BM25 hybrid option isn't a separate model: it blends keyword-match scores with embedding scores, which is cheap and helps with exact terms like product codes and policy numbers.  When to add it (30 sec)Add reranking when diagnostics show the right answer is in the candidate list but not at the top. That's high recall, low precision. And only when the latency budget allows the extra step. For NorthStar, the recommendation is to rerank policy document retrieval. Policy questions are complex, full of conditions like channel, category and item state, and a wrong policy answer has real cost. Simple product lookups with strong metadata filters may not need it. ## Slide 10
- Where to spend a <1s Latency budgest
- TTFT = Time to First Token
> Notes: This figure shows how I to think about designing a chatbot when we have a hard response-time constraint of roughly one second.  The key idea is that latency is a budget. We should not automatically spend that budget on the largest embedding model or the largest LLM. Instead, we want to spend each additional millisecond where it produces the greatest improvement in end-to-end answer quality.  The left shows an illustrative latency budget. Query processing and embedding might consume 30 to 60 milliseconds, retrieval another 30 to 80 milliseconds, and lightweight reranking roughly 40 to 100 milliseconds. The largest allocation is typically the LLM’s time to first token, or TTFT, at approximately 300 to 500 milliseconds. We also need to reserve time for network and orchestration overhead.  Notice that we’re targeting time to first token rather than waiting for the entire response to be generated. For an interactive chatbot, perceived responsiveness depends heavily on how quickly the answer begins appearing.  The decision about where to invest additional latency follows a diagnostic sequence. First ask: Did retrieval find the relevant evidence? If not, improving the embedding model or retrieval strategy may help. Second: Did the right evidence rank high enough to reach the LLM? If retrieval recall is good but irrelevant documents dominate the context, a lightweight reranker is often a particularly valuable investment. Third: Did the LLM use the evidence correctly? If the correct context is already available but the model struggles with reasoning, synthesis, or instruction following, then moving to a more capable LLM may be justified.  An important systems insight is that adding latency to one component can sometimes reduce total latency. For example, spending 60 milliseconds on reranking might allow us to send three highly relevant passages instead of twenty passages to the LLM. The resulting reduction in context length can reduce LLM prefill time enough to offset the cost of reranking.  To make these decisions empirically, measure retrieval recall, ranking quality, final-answer accuracy and groundedness, along with end-to-end latency. For latency, averages are not sufficient. I would specifically examine p50, p95, and p99 time to first token.  Ultimately, compare several system configurations and plot answer quality against p95 latency. The objective is not simply to build the fastest chatbot or use the most capable models. It is to identify the best quality–latency tradeoff that remains within our service-level requirement.  Key takeaway: Treat latency as an end-to-end optimization budget. Spend milliseconds where they produce the greatest measurable improvement in answer quality.

> Notes: Discussion prompt (optional)"If a better embedding model came out tomorrow, what would it take for NorthStar to switch? How would you prove it's better before paying for the migration?”  What it would take to switch The key point from the slide's consistency rule: you can't swap an embedding model in place. Vectors from different models live in different spaces, so switching means: Re-embedding the whole corpus. Every product description and policy chunk goes through the new model. Cost scales with corpus size and gets paid again on every future re-index. Rebuilding the vector index. The dimensions may change, for example from 1,024 to 3,072, which changes the index configuration, storage and memory cost, and search latency. Changing the query path at the same moment. The query embedding must switch in lockstep with the index, or retrieval silently returns garbage with no error. Accepting other trade-offs:  Per-query cost and latency: every search now calls the new model. Data residency: a non-AWS model means text leaves AWS, which was one of the reasons for choosing Titan. Vendor and operational risk: the new model may be less mature, change more often, or be retired. So the question isn't "is it better?" but "is it better by enough, on our data, to justify those costs?"  How to prove it's better before paying for the migration 1. Build a golden retrieval set first. Collect a few hundred real NorthStar queries (search logs and support questions), each labeled with the chunks that should come back. Deliberately include hard cases: synonyms ("sneakers" vs. "running shoes"), product codes and brand names, misspellings, queries that span categories. Public leaderboards like MTEB are a starting filter, not evidence. What matters is performance on our catalog.  2. Compare retrieval offline, on a sample. Embed a representative slice of the corpus with both models and score each with the same retrieval metrics: recall@k, MRR or nDCG, and RAGAS context precision and recall. This costs a fraction of a full migration and answers the core question: does the right chunk show up in the top k more often?  3. Check the end-to-end effect. Better retrieval doesn't always mean better answers. Run the full RAG pipeline on the golden set with each index and compare faithfulness, answer relevancy, and answer correctness. If the LLM was already compensating for retrieval misses, the gain may be small.  4. Check it's real, not noise. Use enough queries, look at confidence intervals or a paired test, and slice the results by category. A model that's better overall but worse on product codes may be a bad trade for a retail catalog.  5. Price it. Estimate the one-time re-embedding cost plus the ongoing query cost, storage, and latency. Put the quality gain and the cost side by side: "+6 points recall@5 for $X up front and $Y per month" is a decision a business owner can make.  6. Validate with live traffic before cutting over.  Shadow index: build the new index alongside the old one (blue/green). Route a copy of live queries to it without showing users the results and compare what each index retrieves. A/B test: then send a small share of real traffic to the new index and watch business signals such as search click-through, add-to-cart, and support deflection.  7. Cut over with a way back. Keep the old index until the new one has proven itself, so rollback is a config change, not another multi-day re-embed. Record the embedding model and version with every index. The model-registry idea applies to embeddings too.  The one-sentence answer "We'd switch only if the new model wins on a retrieval benchmark built from our own queries, by a margin that survives a significance check and justifies the re-embedding and running costs, and we'd prove it with a shadow index and a small A/B test before retiring the old index."  One teaching point to draw out: this is the same discipline as the churn model. Evaluate on held-out data that reflects your use case, don't trust small gains on a single run, and promote through a gate with rollback. Embeddings are a model like any other; they just break more quietly when you get it wrong.

## Slide 12
- RAG Evaluation: The hardest part
> Notes: Opening (15 sec)We've spent several slides building a better RAG pipeline: chunking, embeddings, vector search, reranking. But how do we know any of it actually helped? This is the part most teams skip, and it's the hardest part.  Why RAG evaluation is harder (45 sec)Point to the top left. When we evaluated the churn model, ground truth was a fact: the customer churned or didn't. Scoring was automatic, and we got accuracy, F1 and AUC for free. A RAG answer has no single correct output. "Offer 15% off headphones for 14 days" might be a great answer, and so might a dozen others. To judge it, we have to ask whether it's accurate, whether it's supported by our documents, and whether it helps. Those questions need human judgment, or an LLM acting as a judge that we've checked against human judgment.  Split the problem in two (30 sec)Point to the two component headers. The key move is not to evaluate the system as one black box. A bad answer can come from two very different failures: retrieval fetched the wrong documents, or the LLM mishandled the right ones. The fixes are completely different, so we measure the two separately. Frameworks like RAGAS package these metrics for us.  Component 1, retrieval (40 sec)Recall@5: of the queries, how often was a relevant document somewhere in the top 5? At 0.84, we find the right material most of the time.Precision@3: of the three passages we send to the LLM, how many are relevant? At 0.71, roughly one in four passages is noise. Both need a ground-truth dataset: queries paired with the documents that should answer them. Someone has to build that by hand, and that's much of the real work.  Component 2, generation (50 sec)Faithfulness: is every claim in the answer supported by the retrieved context? This is our hallucination check, and at 0.89 it's the strongest score. For NorthStar that matters: an invented discount is a real cost to the business.Answer relevancy: does the answer address what was asked? A faithful answer can still miss the point.Contextual precision: did the answer rely on the relevant parts of the context rather than the noise? At 0.77 it's amber, which connects directly to the Precision@3 score. When noisy passages go in, some of that noise gets used.  Stress that the scores and color thresholds are illustrations. Real thresholds are a business decision.  The NorthStar dataset (30 sec)Point to the top right. For the optional part of Lab 3, the dataset is 50 offer-generation queries like the retention example on the slide, ground-truth documents for each, and three human raters scoring answers from 1 to 5. The baseline pipeline, with no reranking, is compared against the enhanced one, with reranking and hybrid search, on the same test set. Every metric improves. The biggest jump is Precision@3, which is exactly what reranking is designed to fix. The effect also carries downstream: cleaner context lifts faithfulness and contextual precision, even though we didn't touch the LLM. Improving retrieval often improves answers more cheaply than changing the model. Discussion prompt (optional)"If faithfulness dropped from 0.89 to 0.75 after a change, how would you tell whether retrieval or generation caused it? Which metrics would you look at first?”  Faithfulness measures whether the answer's claims are supported by the retrieved context, not whether they're true. So a drop can come from either side: Generation cause: the model had good context and still made claims beyond it. Retrieval cause: the context got thinner or noisier, so the model filled the gaps from its own parametric knowledge. Those claims may even be correct, but they're unsupported by the context, so faithfulness falls.  Metrics to check first 1. Context recall and context precision, on the same eval set, before and after the change. These isolate retrieval. If they dropped alongside faithfulness, retrieval is the prime suspect. If they held steady or improved, look at generation.  2. A per-query breakdown, not just the averages. A drop from 0.89 to 0.75 is an average, so check whether it is concentrated in the queries where context recall fell. If the faithfulness losses line up query-by-query with the retrieval losses, that's strong evidence. If faithfulness fell on queries whose contexts were essentially unchanged, it's generation.  3. The unsupported claims themselves. Sample 15–20 of them and sort them into: Correct but not in context: the model is compensating for missing information, which points to retrieval. Contradicts the context, or invented details: the model ignored or distorted good context, which points to generation.  The decisive test: swap one side Cache the retrieved contexts from both runs, then cross them: Old contexts New contexts Old generator/prompt 0.89 (baseline) ?  New generator/prompt ? 0.75  If old generator + new contexts drops, retrieval caused it. If new generator + old contexts drops, generation caused it. If both partially drop, it's an interaction. For example, more chunks can push relevant text into the middle of a long context, where models attend to it less.  Before blaming either side Check what actually changed. A chunking, embedding, top-k, or reranker change points to retrieval. A prompt, model, or temperature change points to generation. Obvious, but people skip it. Check the judge. If the evaluator LLM or its prompt changed, the metric moved, not the system. Check the noise. On a 50-query set with LLM-judged scores, run-to-run variance can be several points. Re-run the baseline once to see how stable 0.89 is. If this is a discussion question for your reranking slide, it fits well. A common trap is reranking down to top-3 from a previous top-5. Context precision goes up, but context recall can drop, and faithfulness falls because the model starts answering from memory. Retrieval "improved" by one metric and still caused the regression.  Anticipated questions "Can an LLM grade the answers instead of humans?" Yes, and RAGAS does this for several metrics. But LLM judges have biases, such as favoring longer answers, so validate them against a sample of human ratings before trusting them at scale.  "Is 50 queries enough?" It's enough to catch large regressions and compare pipeline variants, not to detect small differences. Grow the set over time, especially with real queries that failed in production.  "Isn't contextual precision a retrieval metric?" In RAGAS itself, yes. Its "context precision" measures whether relevant chunks are ranked near the top of the retrieved list. This slide uses a generation-side reading: whether the answer used the relevant context. Both are useful; be clear which one you're reporting.  "How do you handle raters who disagree?" Measure inter-rater agreement, for example with Cohen's or Fleiss' kappa. Low agreement means the rubric is ambiguous; tighten it with examples of each score.  “XOps angle?" Treat the evaluation set like test code: version it, run the scorecard in CI on every pipeline change, and block deployments that regress key metrics. In production, sample live traffic for ongoing LLM-judge and human review.

Irrelevant context (40 sec)The embedding model doesn't capture what the user meant, so retrieval returns passages that share words but miss intent. Recall the reranking example: a query about electronics returns came back with a buying guide. Detection: precision@3 below 50% on your evaluation set. Fix it in order of cost: add metadata filters to remove obvious mismatches, add a reranker, and only then consider switching embedding models, which means rebuilding the entire index.  2. Outdated context (35 sec)The index was built three days ago, and products have changed since. The model faithfully describes a product that's been discontinued. This isn't hallucination: the model is doing its job on bad data. Detection is easy with a customer-facing symptom and a system metric: index freshness over 24 hours. The fix is operational: automated daily reindexing, plus the freshness gauge from the operations dashboard with an alert when it goes amber.  3. Context window overflow (40 sec)You retrieve too many chunks, or chunks that are too long, and the prompt exceeds the model's limit. Depending on the setup, you get an error, or text silently cut off, often the instruction at the end, which is worse. Fixes: reduce top-K, truncate chunks, or summarize the context. Flag the asterisk: summarizing contradicts the verbatim rule from the prompt engineering slide, because summaries can drop prices and conditions. Prefer a smaller top-K with reranking so the three best chunks go in whole.  4. Hallucination despite retrieval (45 sec)This is the most dangerous one. Retrieval worked: the right context is in the prompt, and the model ignores it, answering from what it learned in training. For NorthStar that looks like a discount that isn't in any active promotion. Detection: faithfulness below 0.80 in evaluation, and in production, the content filter catching prices or codes not found in the context. Fixes: stronger grounding instructions, such as "use only the information provided; if it isn't there, say so," and choosing a model that scores well on faithfulness in your own evaluation. The output validator is your last line of defense.  5. Slow retrieval (35 sec)As the index grows, exact nearest-neighbor search compares the query with every vector, and latency climbs. Detection: retrieval P95 over 100 milliseconds, visible in the end-to-end number. Fixes: approximate nearest-neighbor indexing such as HNSW, which is standard in OpenSearch; fewer embedding dimensions, since Titan v2 can produce 256 or 512 instead of 1,024; and caching results for frequent queries.  6. Inconsistent output format (35 sec)Downstream code expects JSON, and the model occasionally replies in friendly prose instead. At NorthStar volumes, even 1% means dozens of broken offers a day. Detection: JSON parse failures and schema validation errors in the logs. Fixes: an explicit format instruction in the system prompt, validation against a JSON Schema, and an automatic retry when validation fails. Many model APIs now also offer structured output or tool-calling modes that enforce a schema directly. That's the payoff of building evaluation and monitoring in from the start: failures become alerts with known playbooks, not customer complaints. ## Slide 20
- RAGAS: Diagnosing RAG Systems
> Notes: OpeningWe've built a RAG pipeline. How do we know if it's any good, and when it isn't, how do we know what to fix? RAGAS, short for Retrieval-Augmented Generation Assessment, is an open-source framework built for exactly that question.  Why RAG is harder to evaluateA normal LLM app has one moving part. A RAG app has at least two: a retriever that finds evidence and an LLM that writes an answer from it. When the answer is wrong, there are four possible culprits: the retriever fetched the wrong documents, it fetched the right ones but missed something, the LLM ignored the evidence, or the LLM made something up. A single accuracy score can't tell those apart. RAGAS scores each stage separately.  The exampleTake a simple question: "What year was SageMaker introduced?" Our system retrieves some passages and answers "re:Invent, 2017." That's correct, but we still want to know whether it got there for the right reasons.  Retrieval metrics (blue) Context precision asks whether the retrieved chunks are relevant and whether the useful ones are ranked near the top. Low precision means noise: the LLM has to dig through junk. Context recall asks whether retrieval found all the evidence needed. It compares what we retrieved against a reference answer, so this is the one metric that needs ground truth. Low recall means gaps: the answer can't be complete because the evidence never arrived.  Generation metrics (purple) Faithfulness breaks the answer into individual claims and checks each one against the retrieved context. If the answer says 2017 but the context never mentions a year, that's a hallucination, even if 2017 happens to be right. Answer relevancy asks whether the answer actually addresses the question. One caution: it measures relevance, not correctness. A confident, on-topic, wrong answer can still score well, which is why we look at all four together.  The diagnosis (bottom left)Here's where RAGAS pays off. Say our system gets 82% of questions right, and we want to know why the other 18% fail. Precision is 0.91, so what we retrieve is mostly relevant. Faithfulness is 0.95, so the LLM sticks to the evidence. Relevancy is 0.89, so the answers stay on topic. Recall is 0.62, so we're missing evidence.  The verdict is clear: this is a retrieval problem. Swapping in a bigger LLM would spend money on the part that already works. Instead, we'd look at chunking, top_k, hybrid search, reranking, or gaps in the knowledge base itself. That's the core idea: evaluation becomes a diagnosis, not just a grade.  LLM as judge (bottom right)Who scores all these claims? Usually, another LLM acts as a judge, so we don't need people labeling every response.   Two cautions: The judge can be wrong. Spot-check a sample of its scores by hand, especially early on. Recall still needs reference answers. Budget time to write a small ground-truth set for your test questions.  AWS doesn't offer a managed Ragas service. Ragas is an open-source library, and AWS supports it in three ways: Bedrock models can act as its judge, AWS compute and tracking services can run it, and Bedrock has a native evaluation feature that covers much of the same ground. 1. Amazon Bedrock as the Ragas judge and embedding model This is the most direct integration. Ragas' LLM-based metrics (faithfulness, context recall, and so on) need an evaluator LLM, and the Ragas docs show wrapping a Bedrock model (via LangChain's ChatBedrockConverse) as the evaluator LLM, with a Titan model for embeddings. Your eval code stays standard Ragas; only the judge changes. 2. Bedrock Knowledge Bases evaluation (native alternative) Bedrock has a built-in evaluation job type for Knowledge Bases, generally available since March 2025, that uses a foundation model as judge and computes the metrics without any Ragas or custom scoring code. It supports retrieval-only evaluation, full retrieve-and-generate evaluation, and evaluating a RAG system hosted anywhere if you supply your own inference responses. The metrics map roughly onto Ragas: Ragas Bedrock built-in Context precision Context relevance: how relevant the retrieved texts are to the question  Context recall Context coverage: how much of the ground-truth information the retrieved texts cover (requires ground truth)  Faithfulness Faithfulness: how well responses avoid hallucination relative to the retrieved texts  Answer correctness Correctness  Bedrock adds metrics Ragas doesn't have by default, including completeness, helpfulness, logical coherence, and citation precision, plus citation coverage. It also lets you define custom metrics. Treat the mapping as conceptual, not numerical. The judge prompts differ, so a 0.89 Ragas faithfulness and a 0.89 Bedrock faithfulness aren't the same measurement. This is the same "did the judge change?" trap from the last question. 3. Running and tracking Ragas on AWS Compute: a SageMaker notebook or Processing job for ad hoc runs. Lambda or Step Functions if you want evaluation as a pipeline stage. CodeBuild or CodePipeline to gate deployments on eval scores. Datasets: S3 for the versioned test sets and results. Tracking: Amazon SageMaker managed MLflow, to log Ragas scores per run and compare experiments. This fits the MLOps framing well. AWS Labs also publishes an open-source reference implementation that ties these pieces together. The Gen AI Evaluation Toolkit includes a Ragas scorer (faithfulness, answer relevancy, context recall) that uses Bedrock for the LLM and embeddings, orchestrates evaluation with Step Functions, stores content in S3, and integrates with SageMaker MLflow for comparing experiments. It also includes DeepEval and Bedrock AgentCore scorers, which is useful if the course later moves from RAG to agents. For your Northstar labs A reasonable split: Use Bedrock KB evaluation when students need a zero-code, console-driven result. Use Ragas with a Bedrock judge, logged to SageMaker MLflow when you want them to understand the metrics and wire evaluation into a CI/CD gate. That's the more instructive MLOps exercise. Your job is to predict which metric drops for each failure, then run RAGAS and see if you were right. If you can do that, you know how to debug a RAG system, not just run a library.

## Slide 23
- RAG vs. Fine-tuning Performance
> Notes: Opening (15 sec)One of the first architecture decisions on any enterprise LLM project is whether to give the model knowledge through retrieval or by changing its weights through fine-tuning. This slide is about when each one wins, and why the best systems often use both.  The core distinction (40 sec)Point to the guidance panel. This framing comes from OpenAI's 2023 DevDay talk on maximizing LLM performance. The key idea is that RAG and fine-tuning solve different problems. RAG fixes what the model knows at answer time. Fine-tuning fixes how the model behaves. If the gap is facts, retrieve them. If the gap is behavior (format, tone, a new skill like classification), train it.  The research backs this up. Ovadia and colleagues (EMNLP 2024) compared the two for knowledge injection and found RAG consistently outperformed fine-tuning, for knowledge the model had seen in training and for new knowledge alike. Models are simply bad at absorbing new facts through fine-tuning.  Walking the chart (60 sec) Knowledge-Intensive Q&A: RAG leads by a wide margin over fine-tuning alone, exactly as that research predicts. Facts stored in weights are unreliable, can't be cited, and go stale. Style/Format: The result flips. Retrieval can't teach a model to always produce valid JSON or write in your brand voice. Examples in the weights can. Classification: Fine-tuning wins again because this is a new capability, a label space the base model doesn't have. The gold bars: The combination tops every category. The approaches are additive, which is also OpenAI's point: they're layers, not rivals. Stress that these numbers are illustrative. They show the pattern, not a measured benchmark.  Enterprise reality (30 sec)Point to the adoption panel. Menlo Ventures' 2024 survey shows where industry has landed. About half of enterprise AI deployments use RAG, up from under a third the year before. Only 9% of production models are fine-tuned, despite the hype. And 12% already use agentic architectures, which is where these patterns are heading next. RAG is the default; fine-tuning is the specialist tool.  Takeaway (20 sec)Read the banner: RAG first; add fine-tuning if RAG's output quality is insufficient after optimization. This matches OpenAI's recommended order: prompt engineering, then RAG, then fine-tuning. "After optimization" matters. Fix chunking, embeddings, reranking, and prompts before reaching for fine-tuning, which costs more, needs labeled data, and adds a model lifecycle to operate. Anticipated questions "Why is fine-tuning adoption so low if it works?" It requires labeled data, ML expertise, and retraining whenever things change. ## Slide 24
- Lora and qlora: Efficient fine-tuning
> Notes: OpeningOn our decision tree, fine-tuning was the last step for text: after prompting, after RAG. The reason is cost. Fully fine-tuning a 7-billion-parameter model means updating all 7 billion weights and storing gradients and optimizer state for each one. That's over 100 GB of GPU memory, more than a single top-end GPU holds. LoRA and QLoRA make fine-tuning practical by avoiding most of the model.  LoRA: the key idea (left panel)LoRA stands for Low-Rank Adaptation, from Hu and colleagues at Microsoft in 2021. Look at one layer of the model: a big weight matrix W. Freeze W completely. The pretrained knowledge stays exactly as it is. Add a small side path. The input also goes through two thin matrices, A and B, and their output is added to W's. That's the equation: h = Wx + BAx. Only A and B get trained. Why "low-rank"? A squeezes the input down to a tiny dimension r, the rank, often 8 or 16. B expands it back. The bet is that adapting a model to a new task doesn't require changing everything, just a few important directions, and it holds up remarkably well in practice. The numbers make it concrete. One 4096 × 4096 layer has 16.8 million weights. With rank 8, A and B together have about 65 thousand: 0.4% of the layer. We train a fraction of a percent of the parameters and often get quality close to full fine-tuning. One more detail: B starts at zero, so at step zero the model behaves exactly like the original, and training only moves it as far as the data justifies.  QLoRA: go further (middle panel)QLoRA, from Dettmers and colleagues in 2023, asks: if W is frozen anyway, why store it at full precision? It keeps LoRA's design but compresses the frozen base model to 4 bits. Three tricks make that work without hurting quality: NF4, a 4-bit number format designed for how neural network weights are actually distributed. (NF4 (NormalFloat 4-bit) is the 4-bit quantization format. Instead of dividing the numerical range into 16 equally spaced values, NF4 chooses 16 non-uniform values that are better suited to a normal distribution.) Double quantization, which compresses even the small scaling constants used by the quantization itself. Paged optimizers, which move optimizer memory to the CPU during spikes instead of crashing with out-of-memory errors. The adapters themselves still train in 16-bit, so the gradients stay accurate. The headline result from the paper: they fine-tuned a 65-billion-parameter model on a single 48 GB GPU, matching 16-bit fine-tuning quality on their benchmarks.  The memory picture (right panel)For a 7B model, full fine-tuning needs roughly 112 GB just for weights and optimizer state. That's more than one 80 GB GPU. LoRA drops that to about 15 GB, because we only keep optimizer state for the tiny adapters. QLoRA gets to about 5 GB, which fits comfortably on a single 24 GB consumer GPU even with room for activations. That's the difference between needing a cluster and needing a workstation. The tradeoff: QLoRA trains somewhat slower, because the 4-bit weights are unpacked on the fly for every computation. You're trading speed for memory.  Practical takeaways (bottom strip)  Small and swappable. A LoRA adapter is megabytes, not gigabytes. One base model can serve many tasks, with a support-tone adapter, a product-catalog adapter and a legal-summary adapter swapped in as needed.  No slower at inference. You can merge BA into W before deployment, so the served model is the same size and speed as the original.  Key knobs. Rank r (capacity), the scaling factor alpha (how strongly the adapter speaks), and which layers get adapters: commonly the attention projections, often all linear layers.  When to reach for itRemember the ladder: prompt first, add RAG when the model needs your facts, and fine-tune when you need a consistent behavior, style, or format that prompting can't deliver. When you do fine-tune, LoRA or QLoRA should be your default, not full fine-tuning.

## Slide 25
- Foundation model fine-tuning: when and how
> Notes: Brief Presentation Notes — Foundation Model Fine-Tuning: When and How This slide illustrates parameter-efficient fine-tuning, specifically LoRA—Low-Rank Adaptation. The objective is to adapt an already capable foundation model to a specialized task without retraining the entire model.  1. Training data consists of examples of desired behavior. On the left, we provide pairs of instructions and expected outputs. These examples demonstrate what a good response should look like—appropriate terminology, structure, style, and task-specific behavior. The quality and representativeness of these examples are critical.  2. LoRA makes fine-tuning much more efficient. Instead of updating billions of parameters in the foundation model, LoRA keeps the base weights frozen and introduces relatively small trainable low-rank adaptations into selected layers. We train only those additional parameters. This can dramatically reduce GPU memory, compute requirements, and storage compared with full-parameter fine-tuning.  3. What are we trying to change? The bottom example shows the central motivation. The base model already understands language and can write a product description. The problem is that its response may be generic. Fine-tuning attempts to make the model consistently exhibit the behavior demonstrated in our training examples—in this case, retail-specific terminology, structure, and presentation.  An important distinction from RAG is: RAG changes the information available to the model at inference time. Fine-tuning changes the model’s learned behavior. If the problem is that the model doesn’t know the current product catalog, customer history, or company policy, use RAG. If it has the necessary information but repeatedly fails to produce the required style, structure, terminology, or task behavior, fine-tuning may be appropriate. The practical rule is to try prompting and RAG first. Fine-tuning becomes attractive when we have a sufficiently large set of high-quality examples and can demonstrate through evaluation that the simpler approaches aren’t producing the required consistency. The key takeaway: we aren’t building intelligence from scratch—we’re efficiently specializing intelligence the foundation model already has.  When to Fine-Tune (vs. prompt engineering or RAG):✅ Fine-tune when: The base model's behavior is correct, but its domain knowledge is wrong You have 1,000-100,000 labeled examples A consistent output format is required at scale (e.g., structured JSON every time) The task cannot be solved with retrieval (the knowledge isn't in documents)  ❌ Don't fine-tune when: You have fewer than 500 examples (insufficient signal) The base model already does the task well with a good prompt The domain knowledge changes frequently (you'd need to re-fine-tune constantly)  Notes: "LoRA is the practical choice for most enterprise fine-tuning use cases. Full fine-tuning requires significant GPU compute and careful learning rate management. LoRA adds a small number of trainable parameters (the adapter matrices) while keeping the base model weights frozen — achieving most of the benefit at a fraction of the cost."
