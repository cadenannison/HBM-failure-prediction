## Slide 14
- 14
- VPCs and subnets
- VPCs (Virtual Private Cloud):
- Logically isolated from other VPCs
- Dedicated to your AWS account
- Belong to a single AWS Region and can span multiple Availability Zones
- Availability Zones:
- Isolated group of one or more data centers in a Region,
- designed for high availability.
- Subnets:
- Range of IP addresses that divide a VPC
- Belong to a single Availability Zone
- Classified as public or private
> Notes: Amazon VPC enables you to provision virtual private clouds (VPCs). A VPC is a virtual network that is logically isolated from other virtual networks in the AWS Cloud. A VPC is dedicated to your account. VPCs belong to a single AWS Region and can span multiple Availability Zones.  An AWS Availability Zone (AZ) is an isolated group of one or more data centers within an AWS Region, designed to provide independent power, networking, and connectivity for high availability.  After you create a VPC, you can divide it into one or more subnets. A subnet is a range of IP addresses in a VPC. Subnets belong to a single Availability Zone. You can create subnets in different Availability Zones for high availability. Subnets are generally classified as public or private. Public subnets have direct access to the internet, but private subnets do not.

- Public Subnet Route Table
> Notes: An internet gateway is a scalable, redundant, and highly available VPC component that allows communication between instances in your VPC and the internet. An internet gateway serves two purposes: to provide a target in your VPC route tables for internet-routable traffic, and to perform network address translation for instances that were assigned public IPv4 addresses.   To make a subnet public, you attach an internet gateway to your VPC and add a route to the route table to send non-local traffic through the internet gateway to the internet (0.0.0.0/0).   For more information about internet gateways, see Internet Gateways in the AWS Documentation at https://docs.aws.amazon.com/vpc/latest/userguide/VPC_Internet_Gateway.html.

- Storing data in AWS
- Amazon Simple Storage Service (Amazon S3)
> Notes: AWS has many different services where you can find or store your data. You might use some of the following key services.   Amazon Simple Storage Service (Amazon S3) is object-level storage. Thus, if you want to change part of a stored object or file, you must make the change and then re-upload the entire modified file. Amazon S3 enables you to store as much data as you want, in the aggregate that you want. However, individual objects cannot be larger than 5 TB.    By default, data in Amazon S3 is stored redundantly across multiple facilities and multiple devices in each facility. You can access Amazon S3 through the web-based AWS Management Console or programmatically through application programming interfaces (APIs) and software development kits (SDKs). You can also use third-party solutions (which use APIs and SDKs). Amazon S3 includes event notifications that enable you to set up automatic notifications when certain events occur. An example of such an event might be an object that is uploaded to or deleted from a specific bucket. Those notifications can be sent to you, or they can be used to trigger other processes, such as AWS Lambda scripts.   When your training data is in Amazon S3, you might plan to run training jobs several times with different algorithms and parameters. For these runs, consider trying Amazon FSx for Lustre, a file system service. FSx for Lustre speeds up your training jobs by serving your Amazon S3 data to Amazon SageMaker at high speeds. The first time that you run a training job, FSx for Lustre automatically copies data from Amazon S3 and makes it available to Amazon SageMaker. You can use the same Amazon FSx file system for subsequent iterations of training jobs, which prevents repeated downloads of common Amazon S3 objects.    Alternatively, if your training data is in Amazon Elastic File System (Amazon EFS), you should use it as your training data source. Amazon EFS has the benefit of directly launching your training jobs from the service without the need for data movement. The result is faster training start times. When data scientists have home directories in Amazon EFS, they can quickly iterate on their models. They can bring in new data, share data with colleagues, and experiment with including different fields or labels in their dataset. For example, data scientists can use a Jupyter notebook to do initial cleansing on a training set and  launch a training job from Amazon SageMaker. They then can use their notebook to drop a column and re-launch the training job, and they can compare the resulting models to see which one works better.   You might find data in many other places in AWS. These sources include Amazon Relational Database Service (Amazon RDS), Amazon Redshift (which is a managed data warehouse service), and Amazon Timestream. Amazon Timestream is a managed time-series database that is designed specifically to handle large amounts of Internet of Things (IoT) data. You can even spin up your own EC2 instances and host your own database.   You must be able to extract useful data from these sources when you assemble your data for machine learning, which is the next topic.

Now one nice feature of SageMaker endpoints is that you can replace the machine learning model without endpoint downtime. Since I now have an automated re-training pipeline creating new models, and a model registry where I can approve models, it would be best if the deployment of the new models is automated as well. Over time, the number of requests sent to the new model will increase until the new model gets 100% of the traffic. My deployment strategy is more robust by using auto-scaling and canary deployment, my data scientists save time by automating model training, and every artefact is properly versioned. But as your data science team grows, this architecture won't be sufficient.

## Slide 26
- Level 3: Medium MLOps Architecture
- 26
> Notes: So let's look at a slightly more complicated architecture. The next architecture will be more suitable for a growing data science team of between three to 10 data scientists working on several different use cases at a larger company. So again, let's start with the basics. Our data scientists work in notebooks through SageMaker Studio, pulling from various data sources and versioning their code environments and model artifacts. This should look familiar. Also bring back the automated re-training pipeline. Nothing has changed here, I've only made it smaller to create more room on the slide. And finally, I'll bring back Event- Bridge to schedule the re-training pipeline and model registry for storing model metadata and approving model versions. All of this is exactly the same as in the previous architecture diagram. So what about deployment? Well, this is where things change a little. So I have the same deployment setup with SageMaker endpoints and an autoscaling group connected to Lambda and API Gateway to allow users to submit inference requests. However, these deployment services now sit in a separate AWS account. A multi- account strategy is highly recommended, because this allows you to separate different business units, easily define separate restrictions for important production workloads, and have a fine-grained view of the costs incurred by each component of your architecture. The different accounts are best managed through AWS Organizations. Now, data scientists should not have access to the production account. This reduces the chance of mistakes being made on that account, which directly affects your users. In fact, a multi- account strategy for machine learning usually has a separate staging account alongside the production account. Any new models are first deployed to the staging account, tested and only then deployed on the production account. So if the data scientist cannot access these accounts, clearly, the deployment must happen automatically. All of the services deployed into the staging and production accounts are set up automatically using CloudFormation, controlled by CodePipeline in the development account. The next step is to set up a trigger for CodePipeline. And we can do so using Event- Bridge. So when a model version is approved in model registry, this will generate an event which can be used to trigger deployment via CodePipeline. So now everything's connected again, and this is starting to look like a proper MLOps setup. But I'm sure you've noticed I have plenty of space left on this slide. So let's add another feature which becomes crucial when you have multiple models running in production for extended periods of time - that's model monitor. The goal of monitoring machine learning models in production is to detect a change in behaviour or accuracy. To start, I enabled data capture on the endpoints in the staging and production accounts. This captures the incoming requests and outgoing inference results and stores them in S3 buckets. If you have a model monitoring use case, which doesn't require labelling the incoming requests, then you could run the whole process directly on your staging and production accounts. But in this case, I assume the data needs to be combined with labels or other data that's on the development account. So I use S3 replication to move the data onto an S3 bucket in the development account. Now, in order to tell if the behaviour of the model or the data has changed, we need something to compare it to. That's where the model baseline comes in. During the training process as part of the automated re-training pipeline, we can generate a baseline dataset, which records the expected behaviour of the data and the model. So that gives me all the components I need to set up Sage- Maker model monitor, which will compare the two datasets and generate a report. The final step in this architecture is to take action based on the results of the model monitoring report. And we can do this by sending an event to EventBridge to trigger the re-training pipeline when a significant change has been detected. And that's it for the medium MLOps architecture! It contains a lot of the same features used in the small architecture, but it expands to a multi-account setup, and adds model monitoring for extra quality checks on the models in production

## Slide 30
> Notes: This figure illustrates a Retrieval-Augmented Generation (RAG) architecture built on AWS. It separates the system into two distinct workflows: Document ingestion (offline indexing) — preparing knowledge for future retrieval. Query execution (online inference) — answering user questions by combining retrieved knowledge with an LLM. The key idea behind RAG is that the large language model (LLM) does not memorize all enterprise knowledge. Instead, it retrieves relevant information at runtime and uses that information to generate an answer.  Overall Architecture             Offline (Index Creation) Documents      │      ▼ Knowledge Base      │ Chunking      │ Embeddings      │ Vector Database (OpenSearch)  ────────────────────────────────────               Online (Inference)  User  │  ▼ API Gateway  │  ▼ Lambda  │  ├── Retrieve relevant documents  │  ▼ OpenSearch  │  ▼ Relevant Context  │  ▼ LLM (Bedrock)  │  ▼ Guardrails  │  ▼ User Response The top half happens periodically whenever documents change. The bottom half happens every time a user asks a question.  Part 1 — Document Ingestion Flow (Index Creation) The top section builds the searchable knowledge base. This is an offline process.  Step 1: Documents are collected The system begins with enterprise documents such as: PDFs Word documents manuals policies knowledge articles internal documentation These become the organization’s knowledge corpus.  Step 2: Amazon Bedrock Knowledge Bases The documents are sent into Amazon Bedrock Knowledge Bases This service automates much of the RAG indexing pipeline. Instead of writing custom ingestion code, Bedrock manages: document parsing chunk creation embedding generation synchronization  Step 3: Chunking Large documents cannot be embedded as one giant block. Instead they are divided into smaller pieces called chunks. For example: A 100-page manual might become Chunk 1 Chunk 2 Chunk 3 ... Chunk 750 Each chunk represents a small, semantically meaningful section. This greatly improves retrieval quality.  Step 4: Embedding generation Each chunk is converted into a numerical vector. The figure shows an embedding model such as Amazon Titan Embeddings Instead of storing words, the system stores high-dimensional vectors representing semantic meaning. For example "Reset your router"  ↓  [0.14, -0.91, 0.44, ...] Similar ideas end up close together in vector space.  Step 5: Store vectors Those embeddings are stored in Amazon OpenSearch Serverless OpenSearch acts as the vector database. It stores document chunks embeddings metadata Later, similarity search retrieves the most relevant chunks.  Part 2 — Query Path (Retrieval-Augmented Generation) The bottom half executes every user request.  Step 1: User submits a question The user sends a question. Example: “How do I rotate AWS IAM credentials?”  Step 2: API Gateway The request first enters Amazon API Gateway This exposes the application as a secure REST endpoint. API Gateway handles authentication throttling routing HTTPS termination  Step 3: AWS Lambda API Gateway invokes AWS Lambda Lambda orchestrates the RAG workflow. Rather than generating text itself, Lambda coordinates multiple services.  Step 4: Retrieve relevant knowledge Lambda queries Amazon OpenSearch Serverless using the user’s question. OpenSearch performs a vector similarity search and returns the most relevant chunks. For example, it might retrieve: IAM password policy IAM credential rotation guide AWS security best practices Only the relevant sections are returned—not the entire knowledge base.  Step 5: Build the LLM prompt Lambda constructs a prompt that combines the user’s question retrieved document chunks For example: Question:  How do I rotate IAM credentials?  Context:  AWS Security Manual... IAM Best Practices... Credential Rotation Policy... This enriched prompt is sent to the LLM.  Step 6: Bedrock LLM The prompt is submitted to Amazon Bedrock using an LLM such as Claude. Unlike a standalone chatbot, the LLM now has access to current enterprise information retrieved from OpenSearch. It generates a grounded answer based on both: its pretrained knowledge the supplied document context This significantly reduces hallucinations and enables answers about private organizational data.  Step 7: Guardrails The generated output passes through Bedrock Guardrails Guardrails enforce safety and governance policies. Examples include: blocking harmful content filtering sensitive information preventing prompt injection enforcing organizational response policies Only approved responses continue.  Step 8: Return the response Lambda returns the filtered answer to API Gateway which delivers it back to the user.  Why the architecture is split into two halves One of the most important concepts illustrated by the diagram is the separation of indexing from inference. Top half (offline) Runs only when documents change. Purpose: Build a searchable knowledge index.  Bottom half (online) Runs for every user request. Purpose: Retrieve only the most relevant information and use it to answer the current question. This separation keeps user interactions fast because the computationally expensive work of parsing documents and generating embeddings has already been completed.  The role of each AWS service Service Responsibility Amazon Bedrock Knowledge Bases Automates document ingestion, chunking, embedding, and synchronization. Embedding Model (e.g., Titan) Converts text chunks into vector embeddings. Amazon OpenSearch Serverless Stores vectors and performs semantic similarity search. Amazon API Gateway Receives user requests and exposes the application endpoint. AWS Lambda Orchestrates retrieval and prompt construction. Amazon Bedrock (LLM) Generates responses using both the query and retrieved context. Bedrock Guardrails Applies safety, compliance, and output filtering before returning results. Overall, the diagram demonstrates how a RAG system grounds an LLM’s responses in an organization’s own documents. By retrieving relevant context from a vector database at query time, the architecture improves answer accuracy, keeps information current without retraining the model, and supports enterprise governance through services such as API Gateway, Lambda, and Bedrock Guardrails.

## Slide 44
- What Terraform is doing
- Terraform is a tool that reads text files describing cloud resources (.tf files, written in a language called HCL) and makes AWS match them.
- In Part A you clicked through the console; in Part B you write down what you clicked and let Terraform do the clicking.
- The payoff is that the description is code: you can review it, version it in git, re-run it, and tear it down exactly.
- By default state is a local file. The lab stores it in an S3 bucket instead (a remote backend) for two reasons: a laptop file can be lost, and a DynamoDB table can hold a lock so two apply runs cannot corrupt state at the same time.
- This creates a chicken-and-egg problem: Terraform cannot create the bucket that stores its own state, because it needs the bucket before it can start.
- That is why Phase 3 runs a plain shell script (bootstrap-state.sh) to create the bucket and table before terraform init in dev.
- Docs: State, Remote state, S3 backend (includes the DynamoDB locking section), Backend configuration.

## Slide 47
- Terraform Modules, variables, locals, outputs
- A module is a directory of .tf files that describes one piece of the system. The lab has four (vpc, storage, iam, sagemaker) so each can be reasoned about, tested, and reused independently.
- The environments/dev directory is the root module that calls the four child modules and passes values between them. Modules, Module blocks.
- A variable is an input to a module (var.project). It is how the same module produces northstar-dev-vpc in AWS and northstar-local-vpc in LocalStack: the code is identical, only the input changes. Input variables.
- A local is a named expression computed inside a module (local.bucket_name), used to avoid repeating a long string. Local values.
- An output is a value a module exposes to its caller (module.vpc.vpc_id), and at the root, what terraform output prints. The verify script reads outputs, which is why they must be uncommented. Output values.
- "${var.project}-${var.environment}-vpc" is string interpolation: the ${…} part is replaced with the variable's value. Strings and templates.
- When one resource refers to another (vpc_id = aws_vpc.this.id), Terraform infers a dependency and creates them in the right order. You never write "create the VPC first." Resource dependencies.

- 9. Enterprise AI Organization Operating Models
> Notes: Federated and Governed Self-Service both distribute AI development to business/domain teams. The difference is where the operational burden lives and how governance is enforced. A useful shorthand is: Federated = “Here is the common platform and the rules; domain AI teams still engineer and operate their solutions.”Governed Self-Service = “Here are paved roads that automatically apply the rules; product teams consume them and concentrate on the AI solution.”   The biggest difference is therefore not centralization versus decentralization. Both are decentralized in terms of who builds AI. The distinction is how much complexity the central platform absorbs. 1. In Federated, domain AI teams are still engineering teams Look at column 2. The central platform team provides things such as security, a model gateway, CI/CD templates, model registry, and monitoring/observability. But underneath it you still have dedicated organizations such as Finance AI Team, Marketing AI Team, and Supply Chain AI Team. The figure explicitly says these teams own their: apps, data, features, outcomes. That means the central organization provides reusable building blocks, while each domain team assembles those components into a working AI system. For example, suppose Finance wants an accounts-payable copilot. Under Federated, the Finance AI team might choose the model, construct RAG, integrate Finance data, configure the model gateway, create evaluation tests, configure CI/CD, establish monitoring, and deploy/operate the application—all while complying with enterprise standards. So: Central platform → capabilities → domain AI engineers → AI application Governance is partly technological and partly organizational.  2. Governed Self-Service pushes another layer of responsibility into the platform Column 4 is fundamentally more ambitious. Notice what the platform exposes: Models & RAG → Agents → Data Services → Evaluation & Testing → Deployment APIs And beneath those capabilities is an explicit layer of: AUTOMATED GUARDRAILS — IAM • Policy • Security • Evaluation • Monitoring • FinOps That is the architectural clue. The organization isn’t merely sharing infrastructure. It is turning AI engineering into a set of consumable platform services with policy built into them. The Finance team shouldn’t need to become an expert in IAM implementation, model routing, observability infrastructure, evaluation pipelines, deployment machinery, or cost controls every time it creates an application. Instead: AI platform → governed paved roads → product team → AI application The platform becomes an internal AI product.  The one-question test If you’re trying to classify a real enterprise, ask: “When a business team wants to put a new AI application into production, how much platform engineering does that team itself have to understand and perform?” If the answer is “quite a bit, but they use standardized enterprise components”, you’re probably looking at Federated. If the answer is “very little—the platform exposes self-service workflows/APIs and automatically handles most security, governance, evaluation, deployment, monitoring, and cost controls”, you’re approaching Governed Self-Service. That distinction also explains why the figure positions Governed Self-Service as especially appropriate for organizations with mature platform teams and a high volume of AI use cases: the economics become compelling when the substantial investment in those paved roads can be amortized across dozens or hundreds of AI products.

- S3 Bucket Organization Recommendations
> Notes: This diagram presents a recommended Amazon S3 bucket organization for an enterprise AI/ML platform. Rather than placing all data and artifacts in a single flat bucket, it organizes the bucket into logical top-level domains that match different stages of the machine learning lifecycle. The bucket name shown is a template: s3://[org]-ai-platform/ where [org] would be replaced with your organization’s name. Overall Purpose The structure is designed to: separate raw and processed data isolate reusable features version trained models store experiment artifacts retain evaluation reports centralize configuration files This organization supports scalability, reproducibility, governance, and collaboration across data scientists, ML engineers, and platform teams. Top-Level Folder Structure The bucket is divided into seven logical domains. 1. raw/ This folder stores original source data exactly as it was ingested. Example path: raw/[source]/[year]/[month]/[day]/ Examples: raw/crm/2026/08/01/ raw/iot/2026/08/01/ raw/transactions/2026/08/01/ The diagram emphasizes that raw data should be immutable. Once ingested, it should never be modified. If data changes, a new version or partition should be written rather than overwriting existing files. This provides: reproducibility auditability regulatory compliance recovery from downstream processing errors 2. prepared/ After ETL or data-cleaning processes, the transformed datasets are stored here. Example path: prepared/[project]/[dataset]/[version]/ Example: prepared/churn/customer_features/v3/ This separation keeps raw data isolated while allowing multiple cleaned and transformed datasets to coexist. Versioning ensures that models trained months apart can still reference the exact same prepared dataset. 3. features/ This folder stores offline feature store snapshots. Example: features/customer-risk/2026/08/01/ These are engineered features that have already undergone feature engineering and are ready for model training. Rather than recomputing features repeatedly, training jobs can simply load them from this location. Typical contents include: customer lifetime value rolling purchase averages fraud scores embedding vectors 4. models/ This directory stores model artifacts exported from the Amazon SageMaker Model Registry. Example: models/churn-model/v12/ Typical artifacts include: serialized model files inference containers metadata model cards deployment packages Versioning allows multiple production and historical models to coexist. 5. experiments/ This folder stores artifacts produced during experimentation. Example: experiments/churn-experiment/trial-17/ Artifacts may include: hyperparameters metrics notebooks logs checkpoints plots intermediate outputs These support reproducibility and comparison between experimental runs. 6. evaluations/ This directory stores validation and evaluation reports. Example: evaluations/churn-model/v12/ Typical contents include: confusion matrices ROC curves fairness reports calibration plots bias analyses drift reports benchmark summaries Keeping evaluations separate from the model artifacts makes governance and auditing easier. 7. configs/ This folder contains configuration files used throughout the platform. Examples include: pipeline definitions Terraform modules CloudFormation templates parameter files YAML configurations JSON configuration files Because infrastructure evolves independently of data and models, separating configuration improves maintainability. Why the folder hierarchy matters Notice that most directories continue with additional subfolders rather than storing everything together. For example: models/     churn/         v1/         v2/         v3/ instead of models/     model1.tar.gz     model2.tar.gz Likewise: raw/     crm/         2026/             08/                 01/ instead of raw/     customers.csv This hierarchical organization enables efficient partitioning, versioning, and lifecycle management. Example end-to-end workflow A typical ML project would move through these folders as follows: Raw customer data lands in: ETL jobs clean and transform the data into: Feature engineering produces reusable features in: SageMaker trains a model and stores it in: Training experiments generate artifacts in: Model validation reports are saved to: Pipeline definitions and infrastructure remain in: configs/ This separation makes it easy to trace a production model back to the exact data, features, experiments, and evaluations that produced it. Best Practices Highlighted The green “Best Practices” box summarizes four key recommendations: Partition large datasets by year/month/day to improve scalability and query efficiency. Keep raw data immutable so the original source is always preserved for auditing and reproducibility. Version prepared datasets and model artifacts to support repeatable training and deployment. Use consistent naming conventions across folders to simplify automation and collaboration. Architectural Significance This S3 layout is more than just a naming convention—it reflects the lifecycle of an enterprise AI platform. Each top-level folder corresponds to a distinct stage in the ML workflow: Data ingestion → raw/ Data preparation → prepared/ Feature engineering → features/ Model development and registration → models/ Experiment tracking → experiments/ Model validation and governance → evaluations/ Infrastructure and pipeline management → configs/ By aligning storage organization with the ML lifecycle, the structure improves reproducibility, governance, scalability, and operational efficiency for AI and machine learning projects.

- 9. Enterprise AI Organization Operating Models
> Notes: Federated and Governed Self-Service both distribute AI development to business/domain teams. The difference is where the operational burden lives and how governance is enforced. A useful shorthand is: Federated = “Here is the common platform and the rules; domain AI teams still engineer and operate their solutions.”Governed Self-Service = “Here are paved roads that automatically apply the rules; product teams consume them and concentrate on the AI solution.”   The biggest difference is therefore not centralization versus decentralization. Both are decentralized in terms of who builds AI. The distinction is how much complexity the central platform absorbs. 1. In Federated, domain AI teams are still engineering teams Look at column 2. The central platform team provides things such as security, a model gateway, CI/CD templates, model registry, and monitoring/observability. But underneath it you still have dedicated organizations such as Finance AI Team, Marketing AI Team, and Supply Chain AI Team. The figure explicitly says these teams own their: apps, data, features, outcomes. That means the central organization provides reusable building blocks, while each domain team assembles those components into a working AI system. For example, suppose Finance wants an accounts-payable copilot. Under Federated, the Finance AI team might choose the model, construct RAG, integrate Finance data, configure the model gateway, create evaluation tests, configure CI/CD, establish monitoring, and deploy/operate the application—all while complying with enterprise standards. So: Central platform → capabilities → domain AI engineers → AI application Governance is partly technological and partly organizational.  2. Governed Self-Service pushes another layer of responsibility into the platform Column 4 is fundamentally more ambitious. Notice what the platform exposes: Models & RAG → Agents → Data Services → Evaluation & Testing → Deployment APIs And beneath those capabilities is an explicit layer of: AUTOMATED GUARDRAILS — IAM • Policy • Security • Evaluation • Monitoring • FinOps That is the architectural clue. The organization isn’t merely sharing infrastructure. It is turning AI engineering into a set of consumable platform services with policy built into them. The Finance team shouldn’t need to become an expert in IAM implementation, model routing, observability infrastructure, evaluation pipelines, deployment machinery, or cost controls every time it creates an application. Instead: AI platform → governed paved roads → product team → AI application The platform becomes an internal AI product.  The one-question test If you’re trying to classify a real enterprise, ask: “When a business team wants to put a new AI application into production, how much platform engineering does that team itself have to understand and perform?” If the answer is “quite a bit, but they use standardized enterprise components”, you’re probably looking at Federated. If the answer is “very little—the platform exposes self-service workflows/APIs and automatically handles most security, governance, evaluation, deployment, monitoring, and cost controls”, you’re approaching Governed Self-Service. That distinction also explains why the figure positions Governed Self-Service as especially appropriate for organizations with mature platform teams and a high volume of AI use cases: the economics become compelling when the substantial investment in those paved roads can be amortized across dozens or hundreds of AI products.
